# 演武擂台

《三国：谋定天下》演武大会积分赛的战绩站：一个 Node 进程 + 一个 SQLite 文件 + 一个图片桶。
不用 Docker，也没有前端构建步骤。

按 `演武攻略指南.md`（开发文档 v2.1）实现。业务规则编号（R1–R12）与文档一致。

业务数据只有 SQLite 那一份；图片自 2026-10-15 起存在 Cloudflare R2 上，**由浏览器直传**
（Node 一个字节都不经手 —— 那条隧道的账见「图片压缩」一节）。

### 环境要求

- **Node.js 20.6+**（用到 `--env-file`）。本机实测 v20.20.2 ✓
- 首次 `npm install` 会编译 better-sqlite3（原生模块）
- **不需要任何 R2 的 SDK**：客户端是手写的 SigV4（`r2.js`，纯 Node `crypto`）。
  为什么不引 `@aws-sdk/client-s3`，理由写在 `r2.js` 文件头：发布流水线拦任何
  `package.json` 变更（`.devlocal/release.sh`），而线上的 `node_modules` 不跟 git 走；
  而且手写反而少两个坑。
- 服务端要**出网到 R2 的 API 域名**（`<account>.r2.cloudflarestorage.com`）——
  签发令牌本身不走网络，但复核（HEAD）、删除、备份都要连它；浏览器那半边另需能到
  图片域名。
  ⚠️ 宿主机 ShellCrash 是全局 TUN，这条出网走的是美国节点；而 R2 的 endpoint
  解析出 AAAA 就会走 IPv6 直连（本机 IPv6 不通，症状是 `connection reset`），
  所以 `r2.js` 顶上有一句 `dns.setDefaultResultOrder('ipv4first')`——**别删**，
  它是任何入口 `require('./r2')` 就生效的（包括 `scripts/` 下的那几个）。
- 桶上要配 **CORS**，否则浏览器直传来一个失败一个（配置见 `deploy/DEPLOY.md`）。

> ⚠️ **本机装依赖时的坑**：这台机器 GitHub 域名 DNS 不可解析，better-sqlite3 的预编译包
> 下载通道（GitHub Releases）不可用。已用下面的方式从源码编译成功，换机器重装时照抄：
>
> ```bash
> npm_config_build_from_source=true npm install
> ```
>
> npm registry 与 nodejs.org 走 IPv6 可达，node-gyp 能正常拿头文件。

### .env

```ini
SESSION_SECRET=<64 位随机串，已生成，权限 600>
PORT=3000
HOST=127.0.0.1      # 只监听回环，外部一律经 nginx 进来
DS_API_KEY=sk-...   # 阵容识别的第二路（视觉模型）。2026-10-16 加，见「阵容识别」一节
OCR_URL=http://127.0.0.1:8089/ocr
                    # 阵容识别的第三路（本地 OCR 认自带战法）。2026-10-16 晚加。
                    # 不填 = 这一路关闭，行为与加它之前一致。服务见 deploy/ocr.service

# ---- Cloudflare R2（图片存储，2026-10-15 起）----
R2_ACCOUNT_ID=<账号 ID>
R2_ACCESS_KEY_ID=<S3 API 令牌>
R2_SECRET_ACCESS_KEY=<同上那把令牌的密钥>
R2_BUCKET=<桶名>
R2_ENDPOINT=https://<account>.r2.cloudflarestorage.com
R2_PUBLIC_BASE_URL=https://img.example.com   # 图片的公开域名，页面里就写它
```

那对令牌只需要 **Object Read & Write**、而且只限这一个桶 —— 服务端要删对象、要 HEAD
复核、要列全量（备份 / GC），但日常**不需要** Admin。`r2.js` 的 `setCors()` 是唯一一处
要 Admin 的地方，拿一把临时提权的令牌跑完就撤（见 `deploy/DEPLOY.md`）。

`R2_ENDPOINT` 特意支持 `http://`：测试沙箱里拿一个本地桩顶替真 R2
（`.devlocal/test/r2-stub.js`，端口 3993），断言因此**不必联网、不必真凭证** ——
一旦断言依赖真服务，"跑过了"就会变成"今天网络好"。

这 6 个变量是 `require('./r2')` 的那一刻读的（缺一个就在那一行直接 `throw`），
所以**改完要重启进程**：`sudo systemctl restart yanwu`。

`HOST` 不设或设为 `0.0.0.0` 时 Node 会监听所有网卡——**别这么干**，
那样绕过 nginx 直连 `:3000` 也能登录，等于把限流和反代都架空了。

## 常驻运行

应用本身只是 `node --env-file=.env app.js`。进程守护三选一：

> 📌 本仓库**不含 `deploy/` 目录** —— 里面的 nginx 配置、systemd 单元、`DEPLOY.md`
> 都是照着部署那台机器写的（含本机路径和域名），没有一起公开。下面 B 节和
> 「反代（nginx）」里提到的现成文件，照着自己机器改一份即可。

**A. pm2（文档推荐，尚未安装）**

```bash
npm i -g pm2                    # 需要联网装全局包，装之前先确认
pm2 start app.js --name yanwu --node-args='--env-file=.env'
pm2 save && pm2 startup         # 开机自启
pm2 logs yanwu
```

**B. systemd（推荐，不用装全局包）**

现成单元文件在 **`deploy/yanwu.service`**：

```bash
sudo cp deploy/yanwu.service /etc/systemd/system/yanwu.service
sudo systemctl daemon-reload && sudo systemctl enable --now yanwu
systemctl status yanwu          # 看是否 active (running)
journalctl -u yanwu -f          # 看日志
```

单元里带了 `ProtectHome=read-only` + `ReadWritePaths` 等加固。万一启动失败，
**先注释掉最后那几行加固再试**——那是唯一可能拦住的配置，其余都是常规项。

**C. 前台手动跑**：`npm start`（关掉终端就停）。

### 改代码的先后顺序（模板是热读的，进程不是）

`views/` 下的模板**每个请求都从磁盘现读**，而 `app.js` / `db.js` / `routes/` 是进程启动时
加载一次、之后不再变（`require` 有缓存）。所以本地改完就直接 `systemctl restart yanwu` 的
话，两件事之间有一段空窗：

- 改的是**模板内部**（改文案、调样式）→ 无所谓，刷新即生效，也不用重启。
- 改的是**模板要用的新 locals / 新路由**（比如给 `res.locals` 加了个函数、模板里开始引它）
  → 顺序必须是**先改 `app.js` 并重启，再去改模板**。反过来（先改模板、后重启）中间那几分钟
  上线的是"模板在找这个 locals、进程里还没有"的组合，整页会直接 400
  （EJS 里引用一个没传进来的名字是 `ReferenceError`）。
  ⚠️ 2026-10-14 实测踩到过：加称号章时先改的模板、几分钟后才重启，
  期间有真实请求打开首页看到了 `titleOf is not defined`。
- 同一类坑的另外三种形态：
  - 模板引的是**数据层新加的字段**（比如刚给 `db.getLineupWall` 的每一行挂了 `comments`，
    模板立刻用 `r.comments.length`）→ 旧进程下是 `undefined.length`，报 `TypeError`
    而不是 `ReferenceError`，症状一样是整页 500。同理，改 `schema.sql` 加表必须和
    `db.js` 的查询**同一次重启**，否则"表还没有、查询已经发出去"。
  - **新加的模板文件**（还没有人 include 它）可以先落盘，零副作用 —— 加 `/wall` 就是
    这么办的：先写 `views/wall.ejs`，再改 JS 并重启。反过来做的话，重启那一瞬间是
    "首页已经改道去 `/wall`、而 `/wall` 还不存在"，比不改更糟。
  - **回滚要反着来**：先回滚模板，再回滚 JS 并重启。
  - **往 `.env` 加新变量**同属"要先重启"那一类，而且更硬：`r2.js` / `upload.js`
    是在 `require` 的那一刻把环境变量读进常量的（缺配置直接 `throw`），进程不重启
    就永远看不到新值。`R2_*` 那 6 个、以及由它们渲染进模板的 `data-upload-max-bytes`
    （`maxOutBytes` 是启动时挂到 `res.locals` 上的）都得重启一次才换过来。
- ⚠️ **EJS 的注释里不能出现 EJS 标记**。`<%# … %>` 里只要混进一个起头标记（哪怕是在注释里
  举反例讲"别用某个写法"），EJS 是先按标记把整份文本切碎再逐段解析的，这条注释就被提前截断，
  报出来的是 `Could not find matching close tag`，而且**整页 500**。
  2026-10-14 写评论模板时就这么挂过：首页和 `/wall` 一起 500 了几十秒。

### 反代（nginx）

现成配置在 **`deploy/nginx-yanwu.conf`**，拷到 `/etc/nginx/sites-available/yanwu` 即可。
完整步骤见 `deploy/DEPLOY.md`。

两个容易踩的点，配置里都处理了：

- **`client_max_body_size 1m`**（2026-10-15 从 `64m` 改小）：图片改成浏览器直传 R2 之后，
  提交上来的表单里只剩 `lineup_note` / `score` 两个小字段，字节一个都不进这个进程。
  原来的 64m 是给"一次最多 6 张、单张原图 10MB"那条旧上传路径留的（60MB），
  那条路已经不存在了，留着等于给一个不存在的请求开门。
  **但也别删掉这一行**：删了等于回落到 nginx 默认的 1m，行为一样、意图不明。
- **真实 IP 透传**：`limiter.js` 按 `req.ip` 记登录失败次数。IP 没还原的话，
  经 frp 进来的请求在 Node 眼里全是 `127.0.0.1`，任何人输错 10 次密码就会把**全站**锁 15 分钟。
  配置里用 `set_real_ip_from 127.0.0.1` + `real_ip_header X-Forwarded-For` 还原。
- **反爬虫的执行部分**（2026-10-15 加）：`map $http_user_agent $ai_bot` 拦 AI 爬虫
  （`if ($ai_bot) { return 403; }`），外加一道 `limit_req` 洪水保护。
  声明部分不在这里 —— 那是 robots.txt，见下面的「反爬虫」一节。
  ★ 这一节的「安装」要 root，**命令见 `deploy/DEPLOY.md`**：装完先 `nginx -t`，
  通过了再 `reload`（`-t` 不过时 nginx 继续跑旧配置，站点不会掉）。

只有 `/public`（CSS / JS）交给 nginx 直接发。`/uploads/<名字>` 现在**只剩一条 302 跳板**
（在 Node 里，`routes/uploads.js`）：图片搬到 R2 之后页面上的链接全指向图床域名，
老地址只用来救改造前留下的书签和缓存 HTML。

> **别在 nginx 里给 `/uploads` 加 `rewrite` 直接跳图床**。往 nginx 里写死图片域名等于给
> "URL 拼接"弄出第二处真源（域名在 `.env` 里），还得 sudo + reload 才能改，
> 而且本站有两个入口（隧道 / 直连），两边都得写一遍。放在 Node 里这三条全免。
> 代价是这一跳过隧道（约 1.1s），但它只服务老书签。

缓存头现在由**对象自身的元数据**管（PUT 那一刻由服务端签进签名，见「缓存头」一节），
nginx 这边一个缓存头都没加（它只加了上面那条反爬虫规则）。

## 图片压缩

玩家传上来的图**一律重编码成 jpg、压到 1MB 以下**才允许入库，但**压缩这件事现在发生在
浏览器里**（`public/upload.js`）—— 服务端根本见不到原图，一个字节都不经手。

一次上传走这条线：

```
浏览器                                站点(Node)                      Cloudflare R2
  │ canvas 压缩（阶梯 6 档）                │                                │
  ├── POST /uploads/sign ────────────────▶ │ 配额预检 + 签发 presigned PUT   │
  │ ◀── items[]：url / thumbUrl / headers / token ── 每把 key 一个 HMAC 令牌  │
  ├── PUT 原图、PUT 缩略图（头原样回传） ───────────────────────────────────▶ │
  ├── 令牌写进隐藏 input，form.submit()    │                                │
  └── POST /lineup 或 /score ────────────▶ │ HEAD 复核 → 写库 → 重定向       │
                                           └── 没复核过的对象删掉 ─────────▶ │
```

顺序是**先全压完 → 再签名 → 再统一 PUT**，三个理由：

- 压完才知道有没有解不开的图，失败时**一个对象都不会产生**（不产生孤儿）；
- 令牌有效期只有 10 分钟（`SIGN_TTL`），先签名再慢慢压会把有效期吃掉 ——
  老手机压一张就要好一会儿（上限 2026-10-16 从 6 张收到 1 张，这条理由变弱了，
  顺序本身仍然是对的）；
- 领令牌那一步顺手做**配额预检**（赛期在不在、阵容额度够不够），放在压完之后调，
  用户就不会白压白传一批注定被拒的图（那批字节走的是他自己的流量和 R2 的带宽）。

**为什么必须在浏览器里压**：从前是"手机原图 3~5MB，走 frp 那点带宽传一张要等半天"；
现在字节不过那条隧道了（这是本次改造的全部意义），但理由仍然成立 ——
R2 的存储和流量是钱也是配额，大图在阵容墙上打开也慢。

压缩阶梯在 `public/upload.js` 的 `LADDER` 里，**第一档特意不缩尺寸**，只重编码：

| 输入 | 输出 | 尺寸 |
|---|---|---|
| 2844×1280 游戏截图，1.16MB | **319KB** | 不变（2844×1280） |
| 1238×619 PNG，0.97MB | **133KB** | 不变，并转成 jpg |
| 4000×3000 噪点照片，11.6MB | **934KB** | 降到 1920×1440 |

游戏截图这种大片纯色的图，只重编码就够了，没必要动人家的像素；真正压不动的
（大面积噪点的照片）才逐档降长边和画质，直到进 1MB。
（上表三个数是服务端 sharp 时代量的，canvas 复现的是同一套阶梯，结论不变。）

阶梯一共 6 档，**长边 2560 出现两次**（只换质量、不重画 canvas）：

```
[2560, .85] [2560, .72] [1920, .75] [1600, .70] [1280, .65] [1024, .60]
```

压缩的**上限**只有一处真源：`upload.js` 的 `MAX_OUT_BYTES`（默认 1MB）。
它由 `/uploads/sign` 随响应下发、由模板渲染进 `data-upload-max-bytes`，
前端拿它当"别白传"的前置判断；服务端提交时**再对每个对象 HEAD 复核一遍**
（存在 / ≤1MB / `Content-Type` 是 jpeg，原图和缩略图都要有），不通过就删掉并打回。

顺带解决的两件事（现在都在 canvas 那一侧，教训照旧有效）：

- **EXIF 方向**：手机竖拍照片的方向记在 EXIF 里，而 canvas 重编码会把 EXIF 丢掉。
  所以解码走 `<img>` 而不是 `createImageBitmap(file)` —— 现代浏览器渲染 `<img>` 时
  默认就按 EXIF 摆正（`image-orientation` 的默认值 `from-image`），`drawImage` 拿到的
  已经是摆正的位图。（从前这一步是 sharp 的 `.rotate()`。）
- **PNG 的透明区**：jpeg 不支持透明，会变黑。所以 `scaleCanvas()` 先给 canvas 填一层
  白底再 `drawImage`，和从前 sharp 的 `flatten({background:'#ffffff'})` 一个效果。

> **已经是"合规 jpeg"的图原样放过**（`renderVariants` 里的 `passthrough`：`image/jpeg`、
> 体积已达标、长边不超 2560）—— 重编码会白丢一代画质，而"换一张阵容图""重新提交"
> 这类场景里它才是常态。开这条捷径不影响安全：对象上的 `Content-Type` 是**签进签名里的**
> `image/jpeg`，与文件真实内容无关，所以开不出"往图片域名塞 HTML"的口子。

### 拖拽上传

`/lineup`（阵容截图）和 `/score`（积分截图）两个页面的文件框都能**直接拖文件进去**。
`public/upload.js`，原生 JS，没有构建步骤。

做法是把拖进来的文件**灌进那个原生 `<input type="file">`**
（`input.files = dataTransfer.files`）。灌进去之后，上面那一半（压缩 → 签名 → 直传）
读的正是这个 `input.files`，所以**拖拽和点选在脚本眼里是同一条路**，
服务端完全不知道有拖拽这回事 —— 它现在连文件都收不到了。

所以**拖拽**是**增强**，不是依赖。三种情况下页面退回原来的样子，点 input 选文件一切照旧：

- **JS 关了 / 脚本没加载**：虚线框、提示、结果一行都不会出现（那些 DOM 全由 JS 生成，
  模板里没有）。不在没有 JS 的页面上留一句「可以拖进来」的空头支票。
- **浏览器太老**：Safari < 14.1、Firefox < 62 不给 `input.files` 赋值，脚本开头探一下，
  赋不进去就整段不启用。
- **触摸为主的设备**（手机、平板）：`(hover: none) and (pointer: coarse)` 时整段跳过 ——
  那边本来就是点一下从相册选，摆个拖不动的框纯属添乱。
  （这个 `return` 只在拖拽那一半**之前**，上传那一半手机照样跑 —— 见 `public/upload.js`
  里那句"别把 return 提到它前面去"。）

#### ⚠️ 但没有 JS 就**传不了图**（2026-10-15 起）

从前这两半都是增强：脚本没加载、浏览器太老、"点 input 选文件、提交、服务端收下文件"
照旧。图片改成浏览器直传 R2 之后**这条路没了** —— 服务端不再经手字节，没有任何东西
能替浏览器把文件送进桶里。这是本次改造的**已知功能降级**，页面上用 `<noscript>` 明说了
（`views/lineup.ejs` / `views/score.ejs`），而不是留一个点了没反应的按钮让人猜。

降级的范围**只有传图这一件事**：改积分、改阵容说明、评论、打分这些一个字都没受影响 ——
它们本来就不依赖 JS。拖拽那一半的降级行为也一个字没变（见上面三条）。

### 表单上的三个钩子（以及两个"不能有"）

`views/lineup.ejs` / `views/score.ejs` 那两张表单上挂着：

| 钩子 | 用途 |
|---|---|
| `data-upload-kind` | `lineup` / `score`，领令牌时的用途 |
| `data-key-field` | 提交时用哪个字段名承载令牌（`images` / `image_key`） |
| `data-upload-max-bytes` | 单张压完后的上限，由服务端渲染进来（唯一真源在 `MAX_OUT_BYTES`） |

两条**必须保持的"没有"**，都是为了同一件事 —— 让字节绕开这个进程：

- 表单**不能有 `enctype="multipart/form-data"`**。留着的话浏览器按 multipart 发，
  而服务端已经没有 multer 了（**没有任何 multipart 解析器**），`lineup_note` / `score`
  会**静默丢失** —— 表现是"说明保存不上"，特别难查。
- 文件 input **不能有 `name`**。这是"字节不再经手服务端"的**结构性保证**：
  没有名字，浏览器就不会把文件放进表单提交，不是靠 `input.value=''` 之类的技巧。

拖进来之后客户端会先筛两道，都只是为了少让人白等一次上传（真正的把关在两处：
`/uploads/sign` 的配额预检，以及提交时的服务端 HEAD 复核）：

| 情况 | 表现 |
|---|---|
| 非 jpg / png / webp | 挡在外面，并说明忽略了哪个文件（判据和上传那一半的 `COMPRESSIBLE` 一致 —— 从前它对应的是服务端 multer 的 `EXT` 表，那张表随直传一起没了） |
| 一次拖的比剩下的额度多 | 截到剩余额度，说明「多出来的 N 张没收」（额度来自模板的 `data-max`） |
| 额度已满（`data-max="0"`） | 直接说「已经传满了，先删掉几张再拖」，一个字节都不传 |
| 拖的是选中的文字 / 页面链接 | 不算数：不亮框、不动 input |
| 拖到虚线框**外面** | 拦住浏览器打开该文件的默认行为（否则整页跳走），提示往框里拖 |

结果（选了几张、多大、忽略了什么）显示在框里一行提示上，带 `aria-live` 让读屏软件也念一句。

三个浏览器上的坑，改的时候别踩：

- **`dragover` 必须 `preventDefault()`**。不拦的话浏览器判定这个位置「不接受放置」，
  `drop` 事件根本不会来，松手时反而按默认行为去打开那个文件。
- **灌文件之后原生控件自己会更新**（显示「2 files selected」），而上传那一半读的正是
  这个 `input.files` —— 所以拖进来的图和点选的图走的是**同一段代码**，
  不存在"拖拽有另一条上传路径"。
- **虚线框不能「淡入」**。`.drop-field` 上有 `border-color` / `background-color` 的过渡
  （拖进来时描边转金要用它），而加类的瞬间浏览器会从「没有框」过渡到「有框」，
  页面一打开就能看见框淡入 140ms。所以 `upload.js` 加类前先把 `transition` 压成 `none`、
  逼一次重排让它落地，再加类。**调试这个的时候很容易被自己骗**：截图若正好落在过渡中间，
  读到的 computed style 是过渡的**起始值**（描边是 `currentColor`、底色透明），
  连 `!important` 都「不生效」—— 那不是层叠问题，是过渡还没跑完。

`upload.js` 和样式表一样带 `?v=<文件 mtime>`（见 `app.js` 的 `assetVer`）：
nginx 给 `/public/` 盖了 `max-age=604800`，不带版本号的话改完这个脚本，
浏览器一周都不会来取新的 —— 那段时间里用户看到的是「拖了没反应」。

### 缩略图（那几格小格子不下原图）

**页面上所有 <img> 显示的都是一张缩略图，原图只在"点开看大图"时才下。**
2026-10-14 加的，起因是一个真实反馈：投完分页面重刷很慢 —— 顺着查到隧道上，
发现一屏二十个小格子一直在喂 350~390KB 的原图，实测首访要 5.19MB / 35.7s。

| | 原图 | 缩略图 |
|---|---|---|
| 文件名 | `<uuid>.jpg` | `<uuid>.jpg` **+ `.thumb.jpg`** |
| 长边 / 画质 | ≤2560 / 见 `LADDER` | 640 / q72（`THUMB_EDGE` / `THUMB_Q`） |
| 一张多大 | 350~390KB | **23~30KB**（约 13 倍） |
| 谁在显示它 | 弹层、`<a target="_blank">` | `.shot-frame img`、`.thumb`、`.thumb-lg`、`.gallery img` |

名字是**原文件名后面直接接后缀**，不是加在中缀（`<uuid>.thumb.jpg`）。两个原因：

1. 反推回原图必须是**纯字符串切一刀**（`.jpg` / `.png` 加在中缀就分不出来了）——
   老链接的 302（`routes/uploads.js` 把 `x.jpg.thumb.jpg` 折回 `x.jpg` 判形状）
   和全站的 `thumbUrl` 都靠它。
2. **桶上已经躺着 58 个按这个规则命名的对象**（迁移时一个字节没改名），所以它现在是
   硬约束，不是可以顺手改掉的风格问题。

**只有一条生成路径：上传时在浏览器里做**（`public/upload.js` 的 `scaleCanvas` + `THUMB_Q`），
和原图一起 PUT 上去。从前那两条 —— 上传时服务端做、第一次被要到时 `ensureThumb` 现补 ——
随"服务端不再经手字节"一起没了（`ensureThumb` 整个中间件已删），所以：

- 缩略图**必须**在提交时就已经在桶里。服务端提交时对原图和缩略图**各 HEAD 一次**，
  缺缩略图**直接打回**（`routes/main.js` 的 `verifyUploaded`）—— 从前缺了还能现补，
  现在服务端不碰字节了，缺了就是阵容墙上一个**永久的空格子**。
- 改造前的老图在迁移时**连缩略图一起搬**了，见「搬到 R2」一节。

删除跟着原图走：全站的删图都收在 `upload.js` 的 `removeFile()` / `removeFiles()` 里
（删单张阵容图、换积分截图、删赛期、上传失败回滚），它会把 `<名字>.thumb.jpg` 一起删掉 ——
漏了的话桶里会慢慢积一堆没人引用的孤儿（`scripts/r2-gc.js` 能兜底，但那只是兜底）。

### 缓存头：图片对象一年 immutable

这是「投完分重刷很慢」的根治。打分是 POST → 302 → 回 `/#e<id>`，**每次都要重刷整页**，
而从前图片吃的是 `express.static` 的默认值 `Cache-Control: public, max-age=0`：
页面上二十张图，张张都要回服务器问一遍「变了没」，隧道单程 1.1s ——
实测重刷光这一项 2.3s，几路并发挤在一起时到过 24.6s，而同一时刻服务端渲染只要 **17ms**。
跟服务器一点关系都没有，全耗在来回问上面。

现在这条头**写在对象自己身上**（R2 不会替你加）：

```
Cache-Control: public, max-age=31536000, immutable
```

★ 它是**在 PUT 的那一刻写进对象元数据的**，而且那个 PUT 的 `cache-control`
是**签进 presigned 签名头**的（`r2.js` 的 `presignPut`）：值由服务端在 sign 响应里下发，
前端必须原样回传，改一个字就是 403 SignatureDoesNotMatch。不签会怎样：
对象上就没有这条一年 immutable，浏览器拿到 R2 的默认策略，
上面量过的"重刷时图片请求是 0"**静默回归**。

敢用一年 + `immutable`（连问都不再问）是因为**文件名是 `randomUUID()`，一张图写完就永不改**
（换图 = 换一个新文件名）。
`public` 而不是 `private`（2026-10-15 从 `private` 改过来）：图片现在对所有人一视同仁，
不再有"同一个 URL 对登录的人 200、对游客 404"这回事 —— 见
「图片：所有图现在都公开」一节。

`/public/`（CSS / JS）**没动**，仍是 Node 的 `max-age=0` + nginx 的 `expires 7d`，
靠模板里的 `?v=<文件 mtime>` 失效 —— 那套本来就对，别顺手改。

> 改成缩略图 + 长缓存之后实测（同一条隧道、同一面墙）：
> 首访 **5.19MB / 35.7s → 0.50MB / 4.1s**；重刷时的图片请求 **20 个 → 0 个**，
> 只剩那一趟 47KB 的 HTML。
> （这组数 2026-10-14 量于"图片还在本机、经隧道发"的日子。今天图片走 R2 的公开域名，
> 隧道那一跳没了，但**"请求数为 0"这条判据与文件在哪无关**，仍然是它要守的东西。）

### 点图看大图（页面内弹层）

点任意一张截图（阵容图、积分截图都一样）→ **页面里盖一层显示原图**，不再跳新标签页
（手机浏览器里跳走一次就得按返回，很容易把看到一半的阵容弄丢）。
`public/lightbox.js`，原生 JS，没有构建步骤。

它的判据是 **href 前缀 + DOM**，不是模板上的类名：任何 `<a>` 只要 `href` 以**图片域名**
开头、里面又装着 `<img>`，点它就开弹层。所以首页、赛期详情、`/lineup`、`/score`
那十几处图链接**一个类名都没加**（href 的写法从 `/uploads/<名字>` 换成了 `imgUrl(<名字>)`，
那是域名搬家，跟这条判据无关）。

前缀从 **`<html data-img-base>`** 读（`views/partials/header.ejs` 渲染，值来自 `.env` 的
`R2_PUBLIC_BASE_URL`）—— 静态 JS 里一个字都不硬编码域名。**但保留了 `/uploads/` 兜底**：
用户手上可能还有**缓存的旧 HTML**（nginx 给 `/public/` 盖了 `max-age=604800`），
那些页面里的链接还是老形状；老形状由 `routes/uploads.js` 的 302 送到 R2，图照样能显示。

和拖拽上传一样，这是**增强**不是依赖：

- **模板里的 `<a target="_blank" rel="noopener">` 一个都没去掉** —— 脚本没加载、
  JS 被关了，点图还是"新标签页打开原图"，也就是今天的样子。
- **弹层的 DOM 全部由脚本现建**（`document.body.appendChild`），模板里没有它的 markup：
  没有 JS 的页面上不该多出一个永远打不开的空壳。

| 操作 | 结果 |
|---|---|
| 点图 / 点背景 / 点右上角 × | 关闭（手机上"点哪都能关"最省事） |
| Esc | 关闭，并把键盘焦点**还给点的那张图**（Tab 从原地接着走） |
| ‹ › 或 ← → | 同一组里翻页，**首尾相接**（说明里带「2/3」） |
| Ctrl / ⌘ / Shift 点击、中键 | **不拦**，照旧交给浏览器（新标签页、新窗口、下载） |
| 链接里没有 `<img>` 的图片链接 | 不拦（比如"直接下载"那种纯文字链接） |
| 弹层开着的时候 | 背景页面滑不动（`html.lb-lock`） |

**只有一个人的第一张图** —— 想看到另外几张从前只能跑一趟 `/lineup`。现在图链接上多了一个
`data-shots="url1 url2 …"`（同一个人的全部截图，渲染在 `lineup-gallery.ejs` /
`season.ejs` / `home.ejs` 三处），弹层据此翻页；**不写 `data-shots` 就是单张**，
没有 ‹ › 也没有键盘左右 —— 积分截图就没有写。

卡面上**不再提**这件事（2026-10-14）：阵容卡顶栏那枚 `.badge-wait` 的「共 N 张」已删，
用户的口径是"反正只展示第一张，看不到其他图片"。多图只剩"点开之后"才知道 ——
弹层说明里的「（2/3）」和那句「方向键 ← → 翻页」，以及阵容墙标题下那句
"点图在页面里放大看（能翻这个人的其它截图）"。`data-shots` 一个字没动，翻页能力还在。

尺寸和位置上的三个决定：

- 图是 `contain` 且 `max-height: 86vh`，不是铺满原图尺寸（长边可能到 2560）。和缩略图
  一个道理：阵容图的武将在两侧，裁不得。
- 点开的是 `<a href>` 那个 URL，也就是**原图**（在浏览器里已经压到 ≤1MB、长边 ≤2560）。
  但卡片上那张是缩略图，原图多半还没下过 —— 350KB 要两三秒，弹层不能白等：
  点开时先把页面上那张**已经在本地的缩略图**顶上去，同时悄悄预加载原图，下完再换。
  所以看到的是"立刻有图，几秒后变清楚"，不是一秒钟的黑框。
  翻页（‹ ›）翻到的那几张手边没有缩略图，照旧直接加载原图。
- **窄屏把 ‹ › 挪到底部居中**：超宽阵容图的武将近乎顶到左右边缘，两个圆留在两侧正好
  盖住人家要看的东西。桌面横向有余量，留在两侧。

改的时候别踩的三个坑：

- **`.lb-btn` 必须写死宽度**。Pico 给 `button` 默认 `width:100%`（见「赛期详情」一节的注释），
  不按回去，× 和 ‹ › 会横着铺满整屏。
- **`z-index: 100` 不能省**：顶部导航是 `sticky`，层数不够弹层会被压在它下面。
- **说明文字用 `textContent` 拼，绝不用 `innerHTML`**：`alt` 里是用户自己起的昵称，
  拼进 HTML 就不是文本了。

`lightbox.js` 和样式表、`upload.js` 一样带 `?v=<文件 mtime>`（`app.js` 的 `assetVer`）：
nginx 给 `/public/` 盖了 `max-age=604800`，不带版本号的话改完这个脚本，
浏览器一周都不会来取新的。

### 阵容说明（首页阵容墙）

首页阵容墙每张卡片，除了那个人的第一张阵容截图，下面还展示他自己的**阵容说明**
（`entries.lineup_note`，`/lineup` 页填的那个）。

卡片只有 228px 宽，而说明最长 1000 字，全摊出来会把整行卡片一起顶高，所以用
`-webkit-line-clamp: 5` 截到 **5 行**，超出打省略号。
这一格**永远渲染**（没填说明就是一格空的，带 `.is-blank`）：脚本要把同一排的这一格撑成
一样高，没有这个盒子就撑不起来 —— 见「阵容墙的版面」一节。没 JS 时那格是 `display: none`，
和从前一样不留空盒子。

多出来的这点高度**只顶卡片、不顶图框**（2026-10-14 起）：图框是写死 160px 的，
同一排里那句话长短不一也照样齐（见「显示尺寸」一节）。

两个实现上的坑，改的时候别踩：

- **只能用 `margin` 排版，不能用上下 `padding`**。Firefox（实测 140.13esr）的
  `-webkit-line-clamp` 算盒子高度时不计 padding，给了上下 padding 就会在第 5 行底下
  漏出第 6 行的一条边。所以 `.shot-note` 是 `padding: 0` + 四周全交给 margin。
- **`white-space: pre-wrap` 是故意的**，为了保住玩家自己敲的换行。「一队……／二队……」
  这种分行写的说明压成一大坨就没法看了。

截断这件事是有代价的：**完整说明目前只有 `/seasons/:id` 赛期详情页能看到，而那里只列出
交过积分的人**。传了阵容却没交积分的人，他的完整说明没有任何页面能看到 —— 这是实现
文档里没覆盖到的口子，要么给详情页的「还没交积分」名单也挂上说明，要么以后再说。

### 搬到 R2

存量图（改造前落在 `uploads/` 的那些）要搬到桶上，跑一次：

```bash
node --env-file=.env scripts/migrate-to-r2.js                 # 预演（默认，什么都不写）
node --env-file=.env scripts/migrate-to-r2.js --apply         # 真搬
node --env-file=.env scripts/migrate-to-r2.js --apply \
  --db /home/raving/work/sanmouyanwu/data/app.db \
  --from /home/raving/work/sanmouyanwu/uploads                # 搬线上那一份
```

- **幂等，可反复跑**（先跑一遍，cutover 前再补一遍增量）。
- **默认预演**（沿用从前 `scripts/recompress.js` 立下的约定：破坏性的动作先看清单再动手 ——
  那个脚本已删，约定留着）。
- `--db` / `--from` 默认是相对路径（`./data/app.db`、`./uploads`），**故意不写死线上绝对路径** ——
  这个仓库是公开的。真搬的时候在命令行上把两个都指到线上：**字节的真源是线上 `uploads/`**
  （开发目录那份是某次 pull 的快照，可能缺图或多图），而"该有哪些"的真源是**线上库**。
- **一个本地文件都不删。** `uploads/` 是**回滚底座**：桶上出任何问题，代码退回去就完事了。
- 顺手跳过一个 bug 孤儿：`<uuid>.jpg.thumb.jpg.thumb.jpg`（早期 `makeThumb` 拿缩略图
  去生成缩略图的产物，不在库里、也不该搬上去给公开域名加一个没人要的对象）。

改造之后新传的图**只在 R2 上**，所以另外三个脚本各有各的活：

| 脚本 | 干什么 | 默认 |
|---|---|---|
| `scripts/r2-pull.js` | 把 R2 上的对象**拉回本地**。备份与**回滚**共用这一份实现 | 真写（`--dry-run` 只看） |
| `scripts/r2-gc.js` | 孤儿回收。只碰**形状像本站 key** 的对象、24 小时宽限 | 预演（`--apply` 才删） |
| `scripts/r2-refs.js` | "库里引用了哪些 key"的**唯一真源**（迁移 / GC / 备份核对都从这儿取） | 被上面两个 require |

两个语义要点，别记反：

- **回滚前必须先 `r2-pull`**。要把线上退回旧代码，得先把 cutover 之后新传的对象拉回
  `uploads/` —— 否则"回滚回去发现最近的图全没了"。这个脚本必须在 **cutover 之前**就写好并验过，
  不能等出事再写。
- `r2-gc` 的判据是"不在我的库里 = 垃圾"，本身很危险（桶**共享过一次**：RealOrSteal 的
  `捡漏拍卖行-图标-600.png` 和 `images/` 曾经躺在里面）。所以它有两道防线，**都别拆**：
  ① 只碰长得像本站 key 的（`<uuid>.jpg` / `.jpg.thumb.jpg`），长相不对的只报告不删；
  ② 只删 24 小时以前的对象（用户可能正开着上传页、压了好几张还没点提交）。
  也**不要**把它挂成 cron：删除是破坏性的，手动跑一次最稳。

> ⚠️ **`scripts/recompress.js` 已删**（`npm run recompress` 现在指向一个不存在的文件，
> 是悬空的，留到上线后单独清）。它的前提 —— "图在本机、可以同名覆盖着压" —— 不存在了：
> 图在桶上，而对象名是一年 `immutable` 的（见「缓存头」一节），同名覆盖等于
> **已经看过这张图的浏览器永远拿不到新的那份**。真要重压，只能换文件名（改库 + 重传），
> 所以那个脚本连同它的名字一起退休了。

玩家传的阵容截图里，三支部队各三个武将。这个功能把它们认出来，**用于「阵容里有 T0 英雄就
在卡上高亮」**：`heroes` 是武将库（102 个），`hero_guesses` 是每张图 9 格的识别结果。

### 形态是「机器直接填，玩家事后纠正」

★ 2026-10-16 从"给候选让玩家点"改成了这个 —— **上传完就走，不被 9 个格子拦住**。

在阵容卡上就地改（还是那套单选框 + 「其他」手输 + 「不确定」，`POST /entries/:id/heroes`），
**只有人动过才会写 `decided_at`**，所以"机器填的"和"人核对过的"在库里分得清。

### 卡上只列 T0；「其他」只收库里的名字（2026-10-16 晚，用户定的两条口径）

**一、`reco.ejs` 那一行只渲染 T0。** 从前把认出来的 9 个全列出来，T0 那两三枚金色反而被
淹掉了 —— 而"一眼看出这套带没带 T0"正是这一行存在的全部理由（见 `style.css` 的
`.reco-hero.is-t0` 注释）。现在：

- 只列 `db.T0_HEROES` 里的（**按 key 认**，不是按名字 —— 诸葛亮 / SP诸葛亮 同名不同人）；
- 一个 T0 都没有 → **一枚金胶囊都没有**（加了下节的评级牌之后，那一行**不消失**了 ——
  牌是"一律挂牌"的；真的整行不出的情况只剩"一格都没认出来"）；
- ⚠️ **筛在模板里，不在数据层**：`getSeasonHeroData` 照旧把认出来的全部给出来，
  所以"卡上没显示" ≠ "没认出来" —— 纠正面板（本人 / 管理员）里照旧是全的。
  `test-heroes.js` 第六节专门盯着这一点：它断言那一行里没有非 T0，又断言数据层两格都还在
  （不然"非 T0 不上卡"这条是白过的）。

**二、「其他」手输只能输库里的名字。** 四层：

| 层 | 在哪 | 干什么 |
|---|---|---|
| 名单 | `lineup-gallery.ejs` 的 `<datalist id="reco-hero-names">` | 名单 = `res.locals.heroNames`（`app.js` 每请求从 `heroes` 表算，= `variant + name`，**和候选按钮上印的那个字符串逐字一样**）。**整面墙只渲染一份**，不在每张卡里重复 102 遍 |
| 弹窗挑名字 | `public/reco.js` | 那一格在**面板里**约 300px（面板刚搬进弹窗，见下面「三」），还是放不下输入框。脚本把那个窄框藏起来（**只是不画，value 照样提交** —— 改成 disabled 就会静默丢值），换成一个按钮；点它（或点「其他」那个单选框）弹出**第二层** `<dialog>`：一整行宽的输入框（实测宽屏 564px）+ 打几个字实时筛的名单，点一个就填进去、勾上「其他」、关窗。取消/Esc/点背景三种关法都会把单选框**退回**开窗之前那个 |
| 补全（没 JS 的退路） | 同上 | 脚本没跑、或者浏览器没有 `<dialog>`（探测不到 `showModal` 就整个退出）→ 退回"单选框 + 窄输入框 + 原生 datalist 补全"，**功能一个字都不少**（增强不是依赖，和 lightbox / comments / report 一个约定） |
| 只收唯一对得上的 | `routes/main.js` | `db.findHeroesByName` 必须**恰好返回一条**（显示名 / name / 唯一前缀三档）：0 条 = 库里没这人或打得不像，多条 = 有歧义（「孙」能命中四个孙）。两种都**不写库**，flash 里点名是哪个字没收 —— 只说"有名字没保存"的话，玩家对着九格找不出来 |

**三、整个纠正面板搬进弹窗，入口是卡上的「编辑阵容」按钮**（2026-10-16 晚搬的弹窗；
2026-10-17 用户又改了入口口径：「按照 ocr 的结果直接确定玩家的阵容，并提供玩家本人一个
编辑阵容按钮，点击以后跳到现在的待确认界面，不需要自动弹出窗口了」）：

- 卡上留一颗**「编辑阵容」按钮**（原生 `<summary>`，样式像按钮），**点它**弹出面板：
  九格 **3×3** 排开（实测宽屏每格 303px、手机一列 311px，而卡片里只有 70px / 51px）；
- ⚠️ 表单是**搬**进弹窗的（`appendChild`），**不是另建一份** —— 所以没 JS 时卡上还是那个
  原生 `<details>`，点开就地改，一个字都没变。搬走之后 `<details>` 里只剩那颗按钮，
  卡片高度一点没动（合着的 details 本来也只画一行），`wall.js` 那套逐排等高不受影响；
- **不再自动弹窗**：2026-10-16 那版会在「卡主自己 + 还有没核对过的格子」时自动弹一次，
  2026-10-17 用户明确不要了 —— 服务端不再挂 `data-auto`，`public/reco.js` 里那段也整个删了。
  机器填的结果**直接当阵容用**（认准不准仍然画虚框 + 问号），要改就自己点按钮进来；
- 这一整块**只渲染给能改这张卡的人**：卡主本人和管理员（服务端只给他们候选 JSON）。
  游客和别的成员**连这一块都没有**，所以谈不上弹窗，也没有"要不要确认"这回事；
- 两层弹窗是叠着的（面板 + 手输），Esc 先关上面那层。**关掉上面那层不摘滚动锁** ——
  摘了的话底下的面板还开着、页面却能滚（`syncLock` 每次关窗都看一眼还有没有别的开着）。

两条踩过的坑，改这一块之前先看：

1. ⚠️ **Pico 把 `dialog` 当全屏 flex 遮罩用**（`display:flex; min-width:100%; min-height:100%`，
   内容是给 `dialog > article` 的）。不逐条顶回去的话：`min-width` 赢 `width` → 弹窗永远一屏宽，
   而里面的 body 变成 flex 子项被缩成 fit-content 居中。现象是"窗口只有一小块"，
   看着像 width 写错了，其实是**窗口有一屏大、内容只占中间一小条**（实测 dialog 1280px /
   body 274px，于是九格只排得下 1 列）。`style.css` 第 16 节那一段 `.reco-dlg` 就是干这个的。
2. ⚠️ **`dialog.close()` 是同步的，`close` 事件不是**（规范里是"queue a task"）。所以
   "退单选框"和"摘滚动锁"必须在关窗那一瞬间同步做掉，只挂 `close` 事件的话关掉之后
   还有一小会儿页面状态是错的，而且**测不出来**（断言跑在同一步里，看到的是旧状态）。
   `close` 事件留着兜 Esc —— 那是浏览器自己关的。

这一整块**只有浏览器套件管得了**（`preview/run-browser.sh reco`：一张真卡的面板页跑
1280 / 375 两档）：`<dialog>`、被搬走的表单、被藏起来的输入框、筛选、勾单选框，
没有一样是服务端看得见的；开头那条"进页面一扇窗都没开"钉的正是"不再自动弹"。
服务端管两头 ——**卡上给不给「编辑阵容」按钮**（第六节）和**提交上来收不收**（第四节）。

代价（明说）：`hero_guesses.other_name` 从此**只在"对上了"的时候才有值**，
`/admin` 那块"玩家手输了、库里对不上的名字"变成**考古层**，不会再长。留着是因为
"库里是不是漏了哪个武将"仍然值得回头看一眼 —— 而现在的口径是当场退回，不入库。

### 阵容评级：数「同一支部队里的双人搭配」（2026-10-16 晚）

底表是 `db.LINEUP_PAIRS` —— **用户手工给的 23 组双人搭配**（T0 11 / T1 8 / T2 4），
一行一组、按 key 写并带中文对照，方便和他给的那份名单逐行对着看。
规则在 `db.lineupTier`，**从高往低依次判、命中一条就停**（用户选的口径，撞车时听上面的）：

| 级 | 条件 |
|---|---|
| T0 | 2 组 T0 搭配，或 3 组 T1 |
| T1 | T0 和 T1 都有，或 2 组 T1，或 3 组 T2 |
| T2 | 1 组 T0，或 T1 和 T2 都有 |
| T3 | 其余（默认档） |

三个容易踩的点：

1. ⚠️ **两人必须在同一支部队里**（用户 2026-10-16 定的：是"搭配"，不是"凑齐了"）。
   slot 1-3 / 4-6 / 7-9 各是一支部队，所以 `lineupTier` **不能只拿 key 的集合去查**，
   得先按 slot 分组。`test-heroes.js` 有一条专门钉这个：同样两个人，同一支部队算 T2、
   拆到两支部队算 T3。
2. ⚠️ **它和 T0 高亮是两件事，底表也是两份**：`T0_HEROES` 判"单个武将强不强"（金色胶囊），
   `LINEUP_PAIRS` 判"两个人凑没凑成搭配"（那枚 T 牌）。同一个武将可以两边都在
   （司马懿就是：既是 T0 武将，又和曹丕 / 张春华 / 郝昭各是一组搭配）。
3. **T3 也挂牌**（用户定的"一律挂牌"）—— 所以那一行的渲染判据变成了"有没有认出人来"。
   一格都没认出来的卡才整行不出（实测 21 张卡里 2 张是这样）。

牌子的可信度：**只要有任意一格是"机器填的、没人核对过"，整枚牌子画虚框 + 带 `?`**
（和金色胶囊同一套 `is-auto` 规矩）。判据取全部九格而不是"命中的那几格" —— T3 也是结论，
T3 也可能错。牌子的 `title` 会把**命中的搭配逐组列出来**，别让人对着一个 T1 猜。

配套改了数据层一处：`getSeasonHeroData` 现在**只认卡上摊开的那张图**（第 1 张）并且每项带上
`slot`。前者是老数据的坑 —— 一个 entry 可能有两张阵容图，从前那 3 张卡的武将行是两张**拼起来**
的；评级要按部队分组，拼起来必然算出一个假 T0。现在它和纠正面板（本来就按 filename 查）
口径一致了。
（从前那句有意的设计"对不上也存原文，那些正是最该拿去看的数据"就是在这儿被推翻的，
理由是把这条链上的输入收敛成一种形状：卡上的高亮、统计的口径、`/admin` 的排行榜
全都只面对"库里的武将"。）

### 三路识别，用「多数一致」当置信度

| | 头名对 | 有输出的格子 |
|---|---|---|
| 本地 NCC（`recognize.js`，sharp 多尺度模板匹配） | 41/58 = 70.7% | 58/142 |
| 视觉模型（`recognize-vlm.js`，DeepSeek-V4.1-Flash） | 97/142 = 68.3% | 142/142 |
| **本地 OCR（`recognize-ocr.js`，认自带战法名）** | **111/120 = 92.5%** | 120/142 |

（142 个人工核对过的格子 / 17 张真图；上面那张表的 65%/68% 是更早的一批 63 格样本，
口径不同，趋势一致。复现方式见下面「怎么重跑评测」。）

单看谁也不够用，而且**它们错在不同的格子上**。2026-10-17 起规则收成一条：

- **阵容以 OCR 为准**：这一格 OCR 给了答案就照它填（用户口径「按照 ocr 的结果直接确定
  玩家的阵容」）。实测它最准（92.5% vs 另两路 ~70%），认的还是零撞名的自带战法名。
- OCR 没输出（服务没跑 / 生僻字漏检）→ 按实测准确率退让：**视觉模型 > NCC**。
- `confidence` **不再决定填不填**，只记「这个答案有几路支持」（≥2 路 = `high`），
  喂 `/admin` 的准确率统计。三路各说各的时 support=1 → `low`，但照样填 OCR 的答案。
- 某一路没结果 → 它不参与支持计数，其余照常。

卡上那套「待核对 / 自动弹窗」已经拿掉了：机器填的结果**直接当阵容用**，要改由玩家
点「编辑阵容」自己进来（见上一节）。

**加第三路之前 vs 之后**（同一批 142 格真值上的模拟；当时的口径是"≥2 路一致才算 high"，
现在只用来对照"多一路能把置信覆盖拉多高"）：

| 规则 | 高置信覆盖 | 其中判对 |
|---|---|---|
| 旧：NCC ∩ 视觉模型 一致 | 25/142 = **17.6%** | 25/25 = 100% |
| 新：三票 ≥2 多数 | 95/142 = **66.9%** | 95/95 = 100% |

旧规则给不出结论的 117 格里，第三路**判对 88、判错 9、弃权 20**。
覆盖率翻近四倍靠的就是它 —— 那 117 格里 **84 格是"横屏图上 NCC 一个候选都没有"**。

### 第三路：本地 OCR 认「自带战法名」

**原理。** 每个武将的**自带战法名唯一**（102 个零撞名），而游戏里每张卡的**第一行**
印的就是它。把 102 个名字做成词典，OCR 认字后反查 → 武将。它顺手解决了另外两路
共同的软肋 —— **同名变体**：诸葛亮=草船借箭 / SP诸葛亮=星罗棋布，
孙坚=武烈破虏 / 群雄孙坚=诛凶殄逆。

**服务。** `chineseocr_lite`（DayBreak-u/chineseocr_lite，dbnet + crnn + angle 三个 onnx
共 9.6MB）跑在 `/home/raving/work/ocr/`，**不在本仓库里**（它有自己的 git 和 393MB 的 venv）。
`ocr/server.py` 是个只用标准库的小 HTTP 服务，`POST /ocr` 收图片字节、回文字块。
systemd 单元 `deploy/ocr.service`。**只监听 `127.0.0.1:8089`** —— 这台机器有公网 IPv6
且没装防火墙，绑通配地址等于把它挂到公网上（同 `ddns-go` 那个坑）。

**Node 侧怎么调。** `recognize-ocr.js` 的形状与 `recognize-vlm.js` 完全一致
（`enabled()` / `available()` / `identify(buf)` / `resetCache()`，失败抛错、调用方 catch 降级）。
它**不需要任何 npm 依赖**：Node 20 自带 `fetch`，裁图用已有的 `sharp`。
这一点是**硬约束**：`release.sh` 发现 `package.json` 变了就拒绝发布（线上的
`node_modules` 不跟 git 走），所以第三路必须是进程外调用。

**⚠️ 顺序不能颠倒：是拿文字当定位器，不是"先按坐标裁窗再认字"。**
实测「按 `locate.js` 的头像框逐格裁文字窗」只有 71.8%，而「裁一块宽松的阵容区 →
OCR 一遍 → 让文字块自己聚成 3×3」是 78.2%。差别全在异形宽高比
（2436×1125 = 2.17、2560×1152 = 2.22、1716×889 = 1.93）的图上：那类比例会落到
`locate.js` 的 landscape 族但相对坐标会漂，裁窗整片错位。**OCR 并不天然免疫定位器的洞。**

三个实测出来的坑（都写在 `recognize-ocr.js` 文件头，别重走）：
1. **按"间隙"聚类 → 缺锚点就塌**（51.4%）。一格没认出字会让整行/整列**错位**。
   改成 `splitK()`（强制切出正好 3 行 3 列）→ 78.2%。缺锚点只是那一格空着。
2. **不能拿词典撞三行。**「算无遗策」是郭嘉的自带战法，**同时是可装备战法**，
   会出现在别人卡的第 2/3 行。规则必须是**取格内最靠上的那个锚点**。
3. **别预放大。** 小图确实吃亏，但先放大到短边 1200/1600 再 OCR，准确率**反而略降**。

**已知的残余错因**（占了大半的漏检，不是均匀分布）：诛凶殄逆（"殄"→玲/冷/珍）、
刚烈（双字短名）、平乱定叛。要修就针对这几个名字做字符级纠正表，别去调通用参数。

### `.env` 里的 `OCR_URL`

第三路的总开关（`recognize-ocr.js` 的 `enabled()`）：`OCR_URL=http://127.0.0.1:8089/ocr`。
**不填 = 这一路整体关闭，行为与加它之前完全一致**（零回归）。另一个条件是
`herodata/index.json` 里得有 `skill`（自带战法）—— 没有的话 `available()` 也是 false。

可选：`OCR_TIMEOUT_MS`（默认 60000 —— 服务是串行的，排队时会等）。

**历史图补跑**（加第三路之前识别过的那些）是**手动**的：

```bash
node --env-file=.env scripts/reco-backfill-ocr.js --dry     # 先看要补哪些
node --env-file=.env scripts/reco-backfill-ocr.js           # 真补
```

⚠️ **故意没接进 worker 的 sweep。** `runJob` 是三路一起跑的，把几百张历史图推进队列
会连带**重跑视觉模型**（要花 API token）。同理，`db.filenamesMissingVlm()` 那批也只在
配了 key 时才收。

### 怎么重跑评测

上面的所有数字都来自同一个脚本（本机专属，在 `.devlocal/` 里、不进公开仓库）：

```bash

node --env-file=.env .devlocal/eval-reco.js
# 对线上库的只读快照跑（只读连接，不会写线上库）
YANWU_DB=/home/raving/work/sanmouyanwu/data/app.db node --env-file=.env .devlocal/eval-reco.js
```

真值取 `decided_at IS NOT NULL` 的格子。NCC / 视觉模型用**库里存的快照**
（不花钱、不受视觉模型不确定性影响），只有 OCR 那一路现场跑。

⚠️ 这批格子**偏难**：产品是"机器自动填、玩家出错才去改"，所以核对过的格子里
"原来错、被改对"的比例高于随机上传。数字当方向看，别当生产保证。

改 `recognize-ocr.js` 的定位算法 / 匹配阈值，或改 `merge()` 的合并规则之后**先跑它** ——
单张图看着对，整体可能掉了五个点。

### `.env` 里的 `DS_API_KEY`

视觉模型那一路的总开关（`recognize-vlm.js` 的 `enabled()`）。**不填也照跑**，只是退回
"只有本地 NCC + 本地 OCR"（`confidence` 随之只有一路支持，那只影响 `/admin` 的统计口径，
不影响阵容填谁）。线上要手工往 `.env` 里补 —— 和 `herodata/`、
`deploy/` 一个道理，`release.sh` 不碰 `.env`。

配置项：`DS_API_KEY`（必需）、`DS_MODEL`（默认 `deepseek-flash`）、
`DS_BASE_URL`（默认 `https://api.deepseek.com`）、`DS_TIMEOUT_MS`（默认 180000）。

⚠️ **整张阵容图（含玩家昵称和 UID）会发到这个 API** —— 用户 2026-10-16 明确同意了。
不裁头像只发那 9 个小块是因为**那样认不准**：单张头像问「他是谁」实测答错，
整页图有战法名、兵种角标、上面「武将仓库」的已上阵标记当旁证才认得出冷门武将。

成本约 **6k~15k token/张**（含约 600 字的武将名单），耗时 20~95 秒。跑在后台串行队列里。

### 「定期总结修复」看 `/admin`

`/admin` 的「阵容识别」那一块给三个数 + 一张排行榜：

- **核对过的里面机器是对的** —— 核心质量指标。分母**只算人真的看过的**，
  没人核对的不算（否则数字会随"玩家懒得点"虚高）
- 还有多少格没人核对 —— 这是工作量，不是质量
- **「机器说 X → 玩家改成 Y」排行榜** —— 照着这份名单修 `herodata` 最省事：
  高频配对要么是卡面错画（**有些武将不同皮肤的卡面不一样**，库里的和游戏里显示的
  不是同一张），要么是两个长得像的武将

⚠️ 这个口径改过一次：**旧版的分母把"手输"整类排除在外**，而手输正是机器错得最狠的地方，
于是页面显示 89%/100%、真值是 65%/73%。改版时一并修了。

### 九宫格位置由 `locate.js` 按版面族给（2026-10-16 晚）

从前这里写死一套坐标。**那是错的** —— 游戏 UI 按设备方向换版面，竖屏和横屏是两套排布。
现在 `locate.js` 的 `LAYOUTS` 表按**宽高比**（分界 1.0）挑一族：

| 族 | 版面 | 列 x | 行 y | 框（宽×高） |
|---|---|---|---|---|
| `portrait` | 手机竖屏 | 4.41 / 33.60 / 62.70% | 52.8 / 62.3 / 71.8% | 13.2% × 5.7% |
| `landscape` | PC / 平板 / 宽屏 | 15.5 / 29.0 / 42.5% | 17.0 / 39.0 / 61.0% | 6.0% × 11.0% |

横屏是完全不同的版面：「我的比赛阵容」在左半边横排三行，每格是「小头像 + 三个战法名」，
右边还有一整个武将仓库。框**只框头像本身**，不框整个格子 —— 工作尺度是按框宽反推的，
框越宽工作图越小，头像反而被缩小（见下面那条警告）。

**为什么非做不可**：玩家核对回来的 147 格里，24 张图有 **13 张是横屏**，而写死的竖屏坐标让
横屏 **117 格 NCC 一个候选都没有**。两路一致恒为 0，**置信度信号对一半以上的图不存在**；
候选覆盖率只剩 8%（26 格纠正里只有 2 格答案在选项里），玩家想点都没得点。
顺带一提，横屏的**准确率其实更高**（69% vs 竖屏 62%）—— 缺的从来不是"认得出"，是第二路整个缺席。

实测（`node --env-file=.env .devlocal/reco-layout.js`，24 张真图）：

| | NCC 有候选 | 真值首位命中 | NCC 候选覆盖 | 并集覆盖 | 两路一致那档 |
|---|---|---|---|---|---|
| 旧坐标 | 81/216 = 38% | 41/147 = 28% | 46/147 = 31% | 81% | 25/25 = **100%** |
| 定位器 | **185/216 = 86%** | **66/147 = 45%** | **73/147 = 50%** | **88%** | **40/40 = 100%** |

「并集覆盖」= `NCC 候选 ∪ 库里存着的视觉模型候选`，**这一列才是产品指标**：它等于
"玩家在纠正面板上点得到吗"。单看 NCC 候选覆盖会把横屏算得极惨（那批图的真值是玩家
**从视觉模型的菜单里**选的，那时 NCC 一个候选都没有）。真值一律取 `decided_at IS NOT NULL`
的人核对过的格子 —— **分子分母必须是同一批**，别用机器自动填的格子充数。

> 这里踩过一次，值得记：为了一个查询同时取到"存着的视觉候选"，我一度把真值条件放宽成
> "有 `chosen_key` 就算真值"，于是**机器自动填的格子也进了真值**。而那些格子
> `chosen_key === auto_key === 视觉模型头名` —— 于是"两路一致"必然等于真值，
> 统计出来的 `47/47 = 100%` 里有一大半是**同义反复**，什么都没测。
> 改回 `decided_at IS NOT NULL` 才是 `40/40`。**一个"完美"的数字要先怀疑它在测什么。**

**最要紧的一条是最后一列**：横屏从前 NCC 恒为空 ⇒ 置信度**恒为 low**，
所以"两路一致"（线上标 `high`、直接填、**不打「待核对」**）只在竖屏上产生过。
接上定位器后这一档从 25 格涨到 **40 格，精度仍是 100%** ——
横屏新加进来的那 15 格高置信**没有一格是错的**，担心的"两路一起错到同一个地方"没有发生。
（旁证：旧坐标那一路算出来 25/25，与手工统计完全吻合，说明这把尺子本身是准的。）

竖屏那 11 张的**框**与旧坐标逐像素相同（坐标表里 portrait 那行就是原常数，`test-layout.js` 核过），
识别结果也一致 —— 唯一一处差别是工作宽度因框宽取整落在 538 而不是 540（差 0.4%），
那张图反而多对了一格。横屏 13 张里 11 张从 `0/9` 变成 `9/9`（例外见下面「够不着的地方」）。

⚠️ **工作尺度得跟着框走，不能写死图宽**。`recognize.js` 的模板尺度（46/58/72）是按
"卡框在工作尺度上约 71 像素"标定的，从前 `WORK_W = 540` 是**图宽**。横屏卡框只占图宽 6%
（竖屏 13.2%），固定 540 会把横屏卡框缩到 **27 像素 —— 比最小的模板（46）还小**，
`bestScore` 连可比窗口都没有、一路返回哨兵 `-1`。表现就是**"定位对了也 9 格全灭"**
（2026-10-16 实测踩到过）。现在按 `WORK_BOX_PX = WORK_W × CARD_W` 反推工作宽度，
竖屏算出来仍是 540（基线不动），横屏自己放大到 ~1300 宽 —— 慢几倍，但这是后台队列。

**已知的够不着的地方**（都记在这儿，别当成 bug 重新查）：

- **只有两族。** 1.78 / 1.93 / 1.32 / 1.40 那几个异形比例会落到 `landscape`、
  相对坐标漂一点（框仍压在自己人像上，但会偏）。**漂到不能用的时候用能量尺量出来再补一行**，
  别凭感觉猜。
- **`433×309` 那张修不了**：原始头像是 26 像素，工作图被 `Math.min(meta.width, …)` 挡着不许放大，
  放大也没有信息。它继续走"只有视觉模型"那条路。
- **定位器不判断"这是不是阵容页"。** 非阵容页（武将展示页、抽取初始武将页）照样会算出九个框、
  拿到 0.5+ 的分 —— 也就是说非阵容页现在**可能**出现"两路一致"的高置信自动填。这是已知代价，
  没有顺手加门禁（理由见下）。

**「一个候选都没有时不要发牌」这条是有来历的**：早期版本会把哨兵分数 `-1` 也当有效值参与
贪心分配，结果每张非阵容图都被塞上"库里按拼音排的前 9 个"，看起来像模像样、全是错的。

**为什么是坐标表而不是通用检测器**（试过了，放弃，别重走）：阈值化 → 连通域 → 找「连续三行、
每行正好三块」的点阵。实际跑下来 —— 按 y 聚行时左半边的阵容和右半边的仓库在**同一水平带**，
一行永远不止三列；改成二维单链聚类，两块又被并成一坨；一共五个以上要调的旋钮，9 张测试图
一张都没过；按面积挑最大的块也不行（竖屏图里武将仓库的缩略图比阵容头像更大更多）。
坐标表则是"拿一张该族的截图量一次、加一行"，错了能一眼看出来是哪个数不对。

⚠️ 但 `reco.ejs` 那个 **`<div class="reco">` 是无条件渲染的**（哪怕里面一个字都没有）。
不是笔误：`public/wall.js` 把同一排的 `.shot-head` / `.shot-note` / `.shot-rate` / `.reco`
四块各自撑成等高，少一个盒子就会让有识别结果的卡比旁边高 89px、同一排的评论行整排错开。
盒子本身没有边框底色，看不见。

### 皮肤：素材只能从玩家截图里攒（2026-10-16 晚）

**问题**：玩家核对回来的真改 45 格里，**23 格（51%）塌在三个武将身上** ——
群雄孙坚 14 / 朱儁 5 / 皇甫嵩 4，用户确认这些武将都有**皮肤**。库里每个 key 只有一张
sgmdtx 的基础卡面，而玩家截图里出现的是皮肤。两路识别因此都瞎：NCC 有参考图但每种只有一张，
**视觉模型连一张参考图都没有**（prompt 里只给 102 个名字，它靠自己的记忆认人）。

**素材来源只有玩家自己的截图 + 他们的纠正** —— 每次纠正就是一条带标签的样本
（`filename + slot + chosen_key` 就能反推出这一格是谁）。

```
node .devlocal/harvest-skins.js        # 采集，产出 herodata/skins/ + contact.png
```

- 只取**人核对过**的格子（`decided_at` 非空）。**机器自动填的格子不是标签** ——
  拿它当标签等于把机器的错误当真理喂回模板集，越喂越错。
- 只从**标定过的版面**取材（竖屏 + 横屏 2.0~2.4）。1.93 / 1.32 那些会漂的比例整个跳过 ——
  实测漂出来的框会落到战法文字上，裁出来就是一张字。**用已知不可信的框造训练数据，
  只会把噪声固化进模板集。**
- 每个 key 最多留 3 张、短边 < 64px 的丢掉（小裁图放大也没信息）。
- 产出 `contact.png`（联络表）**是给人过目用的**，用 `contain` 不用 `cover` ——
  裁片是各种长宽比，`cover` 会把两侧切掉、脸偏在一边就像"裁错了"。

**启用（这道人工拷贝就是生产上的闸门）**：`herodata/` 是 git-ignored、线上手工放一份，
所以样本**不经过你手动拷贝就永远到不了线上**，`release.sh` 不会替你同步。
顺序是「先看 `contact.png` → 没问题再把 `herodata/skins/` 拷进线上目录的 `herodata/` 下 →
重启 `yanwu`」。**一条错的纠正会变成一条错的模板，然后污染后面所有图**，所以必须过目。

> ### ⚠️ 2026-10-16 实测：**采了 92 张，结论是暂不启用**
>
> 用能量尺在同样的 24 张图上量（`herodata/skins/` 现在就在开发目录里，线上没有）：
>
> | 定位器 | NCC 候选覆盖 | **并集覆盖（玩家点得到吗）** | 两路一致那档 |
> |---|---|---|---|
> | 不加皮肤 | 50% | **88%** | 40/40 = **100%** |
> | 加皮肤 | **57%** | **88%** | 43/44 = **98%** |
>
> **判据不是"没涨"，是"涨在了没人看得见的地方"**：皮肤让 NCC 自己多认了 10 格，
> 但那 10 格**玩家本来就能点**（视觉模型已经覆盖），所以并集一格没动 ——
> 玩家什么都没多拿到，却换来**一格错的高置信自动填**（`58282b5c`，那格不会打「待核对」）。
> 旧坐标那一路同样从 25/25 掉到 27/28。
>
> 还有一个更要命的：这批样本是**从被评估的这 147 格上采的** —— 等于拿测试集训练、
> 又只在测试集上测。**这么算都只涨一个点**（首位命中 45% → 46%），说明这条路的天花板本身就很低。
>
> **所以：代码留着（`load()` 读 `herodata/skins/`，目录不在就是个空操作，线上现在就是这状态），
> 数据不启用。** 等玩家纠正攒到几百格再看 —— 那时候样本不再来自评估集，数字才有意义。
> 要重开就是把 `herodata/skins/` 拷进线上，不用改代码。

`recognize.load()` 那边有两条不能改错的：

- **往同一个 key 的 `sizes` 里追加，不要另推一条 `templates` 条目。** 下游全部假设
  "一条模板 = 一个 key"（`lib.templates[j].hero` 回填、贪心分配都按 `j` 去重）。
  追加之后 `bestScore` 对每个尺度取 max，语义天然就对。
- **皮肤样本不要套 `REGION`。** `REGION` 是给**官方卡面**去掉角标和名字条用的；
  皮肤样本本身就是游戏头像取景，再套一次等于在脸上再挖一块。

代价：48 个武将共 +138 个尺度（306 → 582），**NCC 大约慢一倍**。量大到受不了时按分数裁剪。

### 势力/兵种是从卡面人工读的，不是抓的

上游 `sgmdtx.com` 的 JSON **不可信**：`bz`（兵种）字段 103 个里 80 个都填「盾」；
`color` 全是 orange；`zy`（势力）基本对但把关平、周仓、徐盛都写成了魏。
所以只用它的**卡面图**，势力/兵种一张张看出来的。详见 `herodata/index.json` 的 `source`。

### 识别为什么这么写

`recognize.js` 文件头有完整交代，三条都是踩出来的：**只在卡框里搜**（整图自由滑窗会撞上
战法文字区的"热点"，一个位置让七八个不相干武将同时拿高分）、**模板必须有下限尺寸**
（否则优化器专挑小模板，分数全是噪声）、**只取头像区不取整卡**（名字条和角标"所有卡都一样"，
会稀释相关性）。另外**9 个武将互不相同**是个硬约束，能挤掉"两格都认成同一个人"。

### 跑在后台

本地 NCC 约 2.5 秒、视觉模型 20~95 秒，而全站是同步请求-响应 —— 所以上传只往队列推
个文件名（`recognize-worker.js`），算的活儿由 `setInterval(...).unref()` 的 worker 串行做。
进程重启后内存队列会丢，启动时扫两批补齐：

- **没有 `hero_guesses` 行的阵容图** —— 全流程补跑
- **有行但 `vlm` 还是 NULL 的** —— 只补视觉模型那一路。
  这条正是改版后"历史图重跑"的入口，不用另写脚本。
  ⚠️ 只在 `DS_API_KEY` 配了的时候才收这批，否则没 key 的环境每次启动都会把历史图全推一遍。

### 阵容上传的两条规矩（2026-10-16 用户加的）

- **每期开期后的第一个周三 12:00 才开放上传**（`db.getUploadOpenAt`），之后一直到结算都能传。
  拦在服务端两处：`POST /lineup` 和 `/uploads/sign`（后者是提前拦，省得玩家白压白传）。
  **已传的图任何时候都能删** —— 窗口一关连传错的都撤不掉才叫坑。
- **每期只允许一张阵容图**（`upload.js` 的 `MAX_LINEUP` 写死 1，不再从 `.env` 读 ——
  它是产品规则不是部署旋钮了）。

⚠️ **这两条和打分截止叠起来有个必须知道的后果**：打分截止是"开期后第一个**周四** 12:00"，
和上传开放是同一套算法、只差一个 weekday。于是：

- 能同时「传阵容」和「被打分」的窗口**每周只有 24 小时**（周三 12:00 ~ 周四 12:00）。
  这是用户要的形态："周三传、周四中午前打完分"。
- 但如果某期是在**周三中午到周四中午之间**开的，上传开放会顺延到下周三、而打分 24 小时内
  就封了 —— **那一期彻底传不了阵容**。`/admin` 会把算出来的开放时刻摆出来并在这种情况下
  报警，开期前就能看见。

## 界面（墨金这一层漆：2026-10-16 改版）

用户这天的要求是「把 UI 和界面再美化一下」，问力度时选的是**大改版**、四个方向全要
（首页看板与排名表 / 阵容墙与阵容卡 / 表格与详情页 / 表单页与手机端）。
这一节记改了什么、以及**为什么这么改** —— 动样式之前先读它。

### 改之前是什么毛病

配色和骨架其实立得住：写死的墨金主题（`<html data-theme="dark">`）、金字宋体标题、
点图弹层、阵容墙分列对齐都留着。问题在**没有层次**。

| 症状 | 根因 |
|---|---|
| 整站看着"一片糊"、卡片浮不出页面 | 页面底 `#14110c` 和卡片 `#1a1611` 每通道只差 6 |
| 满屏小字都"糊" | `--yw-text-dim` 在墨底上小字只有 5 出头的对比度 |
| 没有节奏 | 字号全是手调的零散值（0.66/0.68/0.7/0.72/0.75/0.76/0.8/0.82…），每处都"差一点点" |
| 卡上没有视觉焦点 | 均分/最高/最低三行一样重，`327.8` 和 `190` 看上去同等重要 |
| 表格像马赛克 | 200×160 的大缩略图把版面撑开，昵称列反倒成了最窄的一列 |

| 手机上读不了 | 两列 150px 的小竖卡：昵称被切、三行小字糊成一团、五档按钮贴成一条 |

### 令牌层（`style.css` 第 1 节）

**色号的名字一个都没改**（`--yw-silver` / `--yw-azure-lt` / `--yw-gold-lt` 这些被断言点着名），
改的是值，另加了三组刻度：

- 墨的五档档距拉开（每档差 8~9，从前 6）——**当天晚上整条梯度又一起抬了一档**，见下节「柔化」；
- 描边拆成两支：`--yw-line`（分界）和 `--yw-line-2`（"要看得见"的边：次要按钮、输入框）；
- **金那三档的值刻意不动**：`public/icon.svg` 那方金印用的就是 `#e8cd86` / `#a07c2c`
  （`test-icon.js` 逐字断言了这两个十六进制），页签上的印和页面里的金必须是同一支金。
  要"更亮"就另开一支（`--yw-gold-hi`，只给发丝线 / hover / 焦点用）；
- 新增：字号刻度 `--yw-fs-2xs…4xl`、间距刻度 `--yw-sp-1…8`、面层 `--yw-surface-1/2/3`、
  内高光 `--yw-hi`、投影 `--yw-shadow-1/2`、焦点环 `--yw-ring`；
- 材质：卡片是"顶边 1px 内高光 + 发丝边 + 多层柔和投影"，圆角 8→10 / 12→16。
  **内高光用 `box-shadow: inset` 而不是 `border-top`** —— 它不参与布局，
  `.shot-card` 那几条量尺寸的断言一个都不动。

> 字号刻度有两条**测试量着的**约束，改之前先看 `.devlocal/preview/lb/comment-harness.js`：
> `.rate-k` 和 `details.cmt > summary` 必须同一档（差不超过 0.9 倍 ~ 1.0 倍 +0.5px）；
> `.rate-line` 的字号涨了、它的 `line-height` 必须跟着涨 —— 那条"打分区每条只占一行"
> 用的是"这一行的高 ≤ 1.6 × 它自己的 line-height"。

### 柔化（同一天晚上：把整条墨色梯度抬一档）

用户的反馈是「黑暗背景对比度还是太强了一些，能不能改改背景，让整体更加柔和一点」。
问题出在上一版自己身上：为了做出层次，把**页面底压到了 `#100d09`**、正文提亮到 `#f0e9dc`，
于是正文对底色是 **16:1** —— 比多数暗色主题都冲，而全站最扎眼的那一处恰恰是"背景"。

改法不是去动金、也不是去动布局，而是**把整条梯度整体抬一档、同时把正文压一档**：

| 令牌 | 改版时 | 柔化后 | 说明 |
|---|---|---|---|
| `--yw-ink-1000` | `#070503` | `#15120c` | 图框留白（letterbox）——收益最大的一处 |
| `--yw-ink-900`（页面） | `#100d09` | `#1d1913` | |
| `--yw-ink-800`（卡片） | `#191510` | `#262119` | |
| `--yw-ink-700` / `-600` | `#241e17` / `#2f281e` | `#2f2820` / `#383026` | |
| `--yw-line` / `-2` / `-soft` | `#3a3125` / `#4c4232` / `#2a241b` | `#413728` / `#554936` / `#342d21` | 跟着卡片一起抬，否则线会陷进底色里 |
| `--yw-text` | `#f0e9dc` | `#e5ddcc` | 正文对页面底：**16:1 → 约 13:1** |
| `--yw-text-dim` / `-mute` | `#b6a98f` / `#8b7f6a` | `#bdb09a` / `#978a73` | 底色一亮，这两档在原地会掉到 AA 以下（mute 从 4.9 掉到 4.4），必须跟着挪 |

**两条要点**：

1. **只抬底、不收档距。** 每档之间仍然是 8~9 个色阶 —— 上一版"一层层"的层次全在。
   抬底和收档距是两件事，同时做会把改版成果抵消掉；这次只做了前者。
2. **正文和背景是一件事的两半。** 只把底抬亮、正文原样不动，等于没改（对比度还是 16:1 上下）。
   反过来只压正文、底不动，暗色就"闷"了。两个一起动才落到 13:1 这个"沉但柔和"的位置。

顺带：投影的黑度各收一档（`0.35/0.28 → 0.28/0.22`，底色浅了之后纯黑影子会发脏）、
顶部那道金余光从 `0.10` 收到 `0.08`（底浅了同强度的光会更显眼）、`<meta name="theme-color">`
跟着改成新底色（它上一版就已经是旧的 `#14110c` 了 —— 这个值没人量，最容易忘了跟）。

⚠️ **色板里有两处是硬写的 `rgba()`，不跟着令牌走**，改色号时必须手动同步：
`.topnav` 的背景（半透明页面底）和 `.lightbox .lb-btn` 的背景（半透明卡片底）。
弹层那块底色（`.lightbox` / `--pico-modal-overlay-background-color`）**刻意留得比页面深**
—— 那是看图的暗房，不需要柔。

### 容器放宽到 1340px

Pico 在 1280 视口下只给 `1200px`（≥1536 才 1450），而阵容墙要"一屏仍然 5 张 228px 的卡"
= 5×228 + 4×12 = **1188**：1200 里塞得下，但**浏览器多一条 10px 滚动条就掉成 4 张**。
所以给 `main.container` 加一条自己的规则：`max-width: 1340px` + 自己补左右留白
（Pico 在 ≥576px 那档把 padding 归零、拿 max-width 当留白，1280 视口下那等于一点留白都没有）。
**Pico 这个版本没有 `--pico-container-max-width` 可覆盖**，只能自己写。
顺带把排名表也放开了 —— 它本来就挤。

### 阵容卡（第 9、14 节）

- 卡 200 → **228px 宽**，图框 200×160 → **226×181**（比例仍是 5:4，见「显示尺寸」那节的"双峰"）。
- **均分变成主角**：第一行是宋体大数字 + 亮金，最高/最低退成两行小字副信息。
  用 `:first-of-type:not(.is-empty)` 挑的，**没往模板里加类** —— 没人打分的卡上第一行是
  `.rate-line.is-empty`（「还没有人打分」），那行不能当主角。
- **五档按钮从"金色实心"改成"安静的描边小格"**：从前一面墙 21 张卡就是 105 块金砖铺在那儿，
  把均分这个主角都盖住了。现在默认墨底 + 金字细边，**只有「我打的那一档」（`.is-mine`）是亮的**
  —— 一眼扫过去，先看到分数，再看到"我投了什么"。
- ⚠️ `.shot-card` **必须保持"1px 边框 + 零内边距"**：`wall-harness.js` 有一格算的是
  「图框宽 = 卡宽 − 2」，那个 2 就是这两条边框。要留白就加在卡里面的各块上。

### 手机（第 18 节，断点 640 → 700）

手机从"两列 150px 的竖卡"改成**一行一张的横排卡**：图在左上角（168×134）、
顶栏是它右边的一块高面板、打分区 / 说明 / 评论通栏。

- 图在左是靠 `.shot-frame { order: -1 }`：卡里的 DOM 顺序是「顶栏 → 图框 → …」（桌面竖着排正好），
  横过来顶栏会跑到图前面去。**只动视觉顺序，DOM 一个字节没动** ——
  wall-harness 那条「DOM 顺序 = 按列装」量的是 DOM，不该被这条影响。
- 顶栏面板和图框等高是 flex 的默认 stretch，所以图右边不会空一块。
- ⚠️ **顶栏必须是 `flex: 1 1 0`，不能写 `auto`** —— flex 的换行是在弹性伸缩**之前**
  按各自的基础尺寸决定的：`auto` 时顶栏的基础尺寸就是它内容的宽度（长昵称 + 两枚称号章
  能到 200px 上下），168 + 200 > 卡内宽 → 顶栏被挤到**第二行**、图右边空一大块。
  这条是量出来的（3 张卡红了），不是拍的。
- 打分区通栏之后那三行**不再需要缩字号**（手机上比桌面还宽裕），
  旧那档"四处各收一点点"的补丁整段删了。
- 窄屏的 `.thumb` 跟着降到 104×84；`main.container` 在手机上也补回左右留白
  （Pico 在 <576px 同样把 padding 归零了）。

### 表格（第 7 节）

- `.thumb` 200×160 → **140×112**（`.thumb-lg` 另给上下封顶 240×300）。

## 阵容墙的版面（分列 + 逐排对齐）

2026-10-14 用户对着阵容墙提了两件事，都由 `public/wall.js` 一个人干（挂全站页脚，
找不到 `.shot-grid` 就退出 —— **增强不是依赖**）：

| 要求 | 怎么做 | 没 JS 时 |
|---|---|---|
| **每一行的文字都在一条水平线上** | 按"排"把顶栏 / 说明 / 打分区撑成一样高（写 `min-height`），三块齐了卡片自然等高，图框、均分那三行、按钮行、💬 就都落在同一条线上 | 退回从前：只有 `.shot-rate` 靠 `margin-top:auto` 贴底，顶栏一折行、图框就错开 |
| **展开评论区只顶同一列，别动同一排** | 把 `.shot-grid` 从 grid 换成 N 个 `.shot-col` 竖列（`.is-cols`）—— grid 的行高是整排共享的，撑开一张卡整排（连下面每一排）都会被顶下去 | 退回 grid：点开一张卡会把整排顶下去 |

**顺序不变**：按"第 i 张进第 i % 列数 列"分列，于是第 1 张在第一列、第 N+1 张落到第一列
第二格 —— 视觉上仍然是从左往右、满行换行。**纯 CSS 的 `columns` 是能做到"只顶一列"，
但那样顺序会变成竖着念**（第一列从上到下是第 1、2、3 名），用户不要，所以多写了一段脚本。

几条容易踩的：

- **排是按 `Math.floor(i / 列数)` 分的，不是 `i % 列数`**（后者是"列"）。分错的话会把
  同一列的卡当成一排去撑，等于什么都没对齐。
- **说明那一格必须一起撑**。只撑顶栏和打分区、指望卡片高度去兜的话，富余的高度会落在
  打分区上方的 `margin-top:auto` 里 —— 用户一点开评论区，这点富余先被吃掉，**按钮整排往上
  跳 100px**，然后卡片才开始往下长。三块撑齐之后富余为 0，展开就是干干净净往下长。
- **脚本必须排在 `comments.js` 前面**（见 `views/partials/footer.ejs`）：它量的是布局，
  而 `comments.js` 会按 `#e<id>` 展开某张卡的评论区。反过来引，那张卡的高度会被算进
  "这一排该多高"，用户把评论收起来之后整排还是被撑着。（resize 那条路径躲不开，
  所以量之前会先把展开的合上、量完再还原。）
- **重建的判据要带上卡宽**：断点把卡宽换掉时（桌面 228px，手机一行一张、卡变成通栏），
  列数可能没变，只比列数会把按旧宽度写的 `min-height` 留着。
- **`/wall`（游客那版）走同一段脚本**，用的是同一份 `rows`，所以两边的版面永远一致。
- **手机那一档（≤700px）是"一行一张"**，所以"逐排对齐"在那边**没有对象** —— 一列里每排
  只有一张卡，`min-height` 撑的就是它自己的高度，等于空转。脚本照跑（不跑的话 `.is-cols`
  不生效、列宽算不出来），但**量版面的断言在那边换了另一支**：改量"一行一张"这件事本身
  （只有 1 列、列宽 = 网格内容宽、图在左信息在右、顶栏面板和图框等高、打分区通栏、
  卡不横向溢出）。这一支在 `.devlocal/preview/lb/wall-harness.js` 里，`mobile` 那个分支。

两条已知代价，改的时候别当成 bug：

- **DOM 顺序变成了"逐列"的**（第 1 列整列、再第 2 列整列…），视觉顺序才是逐排的。
  于是 Tab 焦点在五档按钮之间的走法也变成了先下后右 —— 没有干净的修法，不修。
  （手机是单列，这条不适用。）
- **同排里只要有一张卡写了 5 行说明，这一排所有卡的说明格都是 5 行高**（顶栏同理）。
  行高本来也是这么定的（grid 时代就是"最高的那张说了算"），只是空白从"打分区上方"
  挪进了"说明格子里"。（手机单列同理不适用。）

## 打分（成员互评）

站里有**两种数字**，别搞混：

| | 积分（`entries.score`） | 打分（`ratings.value`） |
|---|---|---|
| 谁给的 | 玩家自己上传截图 | 其他成员点一下 |
| 值域 | 0–999999999 任意整数 | 固定五档 `50 / 200 / 250 / 300 / 400` |
| 影响名次 | **是**，积分前两名都算胜者（2026-10-15 起） | **否**，只展示 |
| 影响阵容墙顺序 | 否 | **是**，均分高的排在前面（2026-10-13 起） |
| 影响慧眼等级 | 否 | **是**，结算时按"谁给前两名打了多少"涨等级（只涨不跌，2026-10-13 起） |

打分**不进** `/rank`、不影响名次 —— 名次永远只看积分。它决定两件事：
**首页阵容墙的展示顺序**（均分高的排前面，没人打分的垫底），
以及**结算时的慧眼等级变动**（只会涨，见下面「慧眼等级」一节）。

**但"我投的这一票"不会当场把墙重排**（2026-10-14 起，用户的原话是「打分以后不动，
刷新网页再重排」）。投一票就改均分、均分决定顺序，不拦一下的话整页重刷回来顺序就变了 ——
正在看的那张卡当场跳走，还得重新找它在哪。做法见下面「投票那一跳为什么顺序不动」。

### 怎么投

首页阵容墙每张卡底部五个档位按钮，点一下就投出去。**一个 `<form>` 五个
`<button name="value" value="400">`**，没有 JS —— 和站里其它写操作一样是纯表单 POST。
其中 400 / 300 / 250 三档**每期有名额**（每张卡上那三个按钮可能是灰的），见下面「每期名额」。
投完跳回 `/#e<entry.id>`，落在那张卡上而不是页顶（这一页并不短：标题、按钮、我的卡片
都在墙上面，跳页顶会让人以为没生效）。卡上当场变成「你打了 400」。

**投出去之后按钮还在**：我占着的那一格高亮（浅金底 + 一圈金光 + 加粗），点别的档位就是改分，
上方写着「点别的档位就是改分」。改到哪一档就占那一档的名额，**原来那档的名额当场退回来**
（名额是现数的，见「每期名额」）。点自己原来那一档不会写库，只回一句「没有改动」——
`created_at` 决定"这个分是谁先给的"（见「均分 / 最高 / 最低怎么算」），
手滑点一下不该把署名换人。

### 投票那一跳为什么顺序不动

墙的顺序 = 互评均分降序（见上），而投票就是改均分 —— 所以**投完跳回来的那一页必须照着
刚才那份顺序渲染**，否则人正看着的卡片会当场跳走。做法是"记住上一版的顺序，只顶一跳"：

```
GET  /                     渲染完墙 → 把这版的 entry id 顺序记进 session
POST /entries/:id/rate     第一件事就是置一个一次性标记（被拒的分支也置 —— 被拒的票
                           一个字都没改，更没理由让墙重排）
GET  /（跟的那一跳）        读到标记 → 用 session 里那份顺序排（db.getLineupWall 的第三个
                           参数），读完**立刻删掉标记**
GET  /（用户自己刷新）      标记早没了 → 按最新的均分重排 ✅
```

几条口径：

- **顺序仍然按均分**，没有改成"按积分名次"（用户明确没选那个）—— 冻结只是让"我刚投完
  这一眼"和"我下次进来"之间的差别不刺眼。
- **默认排序一个字都没改**：`/wall`（游客那版）和结算战报（`buildReport`）读的都是默认顺序，
  冻结是首页专用的特例。战报因此**不能**再靠"wall 的第一行就是口碑最好"取数 ——
  那个前提从此有例外，改成显式取均分最大值（口径不变）。
- **顺序串存在 session 里**（cookie-session，整份 session 就在一张 cookie 上），
  一份 id 串约 300 字节，离 4KB 上限很远；断言里有一条专门量它。只在顺序真变了才赋值
  （每赋一次值就重签一张 Set-Cookie）。
- **标记只认"刚投完"的那一跳**（5 分钟以内，`WALL_HOLD_MS`）：投完直接关掉标签页、隔半天
  才回来的人，看到的还是最新的均分序 —— 旧的顺序冻到那时候就成了"顺序怎么是老的"。
- 冻结只在**同一个 session** 里生效：换个浏览器、或者过一阵子重新进来，看到的就是最新的均分序。

### 五条硬规矩

1. **一期内一个阵容只有一票**，但**截止前随时能改**。前者靠
   `UNIQUE (entry_id, rater_id)` 保证，不是靠前端把按钮藏起来；后者不是另一个路由，
   就是再 POST 一次同一个地址（有则 `UPDATE`、无则 `INSERT`，见 `routes/main.js`）。
2. **每期有个截止点：开期后遇到的第一个周四 12:00（北京时间）。** 过点整期封盘 ——
   投不出新票、也改不了已投的，卡片上连按钮都不出，只剩一句「打分已截止」。
   见下一节。
3. **只能投给已经传了阵容的人**（阵容墙上出现的才有按钮；直接 POST 一个没传图的
   `entry` 也会被拒）。
4. **只能投进行中的期。** 期一结算，卡片上就不再出按钮，直接 POST 也会被拒。
   首页在没有进行中的期时会回退显示上一期的结果，那时墙上的分照常展示，只是不能投。
5. **400 / 300 / 250 有名额**：每期每人最多投出 **2 / 3 / 4** 张，50 和 200 不限。
   见下面「每期名额」。

**可以给自己打分**（没做限制，一视同仁）—— 自评的票**也算慧眼**，见「慧眼等级」一节。

### 打分截止（每期开期后第一个周四 12:00）

| | |
|---|---|
| 什么时候封盘 | 每期**开期时间**（`seasons.created_at`）之后遇到的**第一个周四 12:00**（北京时间） |
| 封盘之后 | 这一期投不出新票、也改不了已投的票。卡片上不出按钮，墙上留一句「已于 … 截止，等管理员结算」 |
| 谁能破例 | 只有管理员能**撤掉**某条票（`/admin` 的「打分记录」），或者用【清空本期全部打分】整期清掉。撤掉就是删掉那一行，**过了截止本人也重投不了** |

**为什么要截止**：打分不进名次，但**结算时按"有没有看准前两名"涨慧眼等级**（只涨不跌）。
名次基本明朗之后再补票、再改分，等于照着答案改卷子 —— 投票这件事得在"比赛周结束"之前落定。
**截止前能改**则是为了点错了不用求人：改分是成员自己的事，撤票才是管理员的事。

**截止点是现算的，不落库**（`db.getRateLockAt(season)`，和名额一个路子）：

- 改规则只改 `db.js` 里那两个常数（`LOCK_WEEKDAY` / `LOCK_HOUR_BJ`）；
- **撤销结算**后如果还在窗口里，打分自动重新放开（`created_at` 没动，算出来还是那个点）；
- 时区固定北京：全站时间都按 `Asia/Shanghai` 显示，而北京时间没有夏令时，
  固定 `+8h` 就够，不用 `Intl`、也不用时区库。

**边界**：取的是**严格晚于**开期时间的那个周四 12:00 —— 万一某一期正好卡在周四
12:00:00.000 开启，算下一周，否则那一期一开出来就是封盘的。反过来说，
**周三开期只剩一天多**，所以 `/admin` 的「新建赛期」表单下面会先摆一句
"现在开一期的话，打分截止在 …"，免得开完才发现窗口太短。

**改分的时间戳**：改分会刷新 `ratings.created_at`，和「本人改了积分就刷新提交时间」
同一套道理 —— 时间戳说的是这条评价的时间。所以同分并列时的名字先后会跟着变，
这是对的：把票改成 50 的人，就是**现在**才给的这个 50。

### 每期名额（400 / 300 / 250 有限）

| 档位 | 每人每期最多投出 | 剩下的 |
|---|---|---|
| 400 | 2 张 | 要挑 |
| 300 | 3 张 | 要挑 |
| 250 | 4 张 | 要挑 |
| 200 | 不限 | 想投几张投几张 |
| 50 | 不限 | 同上 |

高分票是稀缺资源：**给谁 400 得先想清楚，不能一口气全撒出去**。
低档位不限，是因为"这阵容我不感冒"本来就该随手能表达，压着人攒着不投反而没意思。
名额按**每期每人**算，和"投给谁"无关 —— 一期一票的规矩（上面第 1 条）保证
一张名额 = 一个人。

**唯一真源是 `db.js` 的 `RATE_QUOTA`**，改规矩只改那一行。

#### 名额不落库，每次现数

`db.getMyQuota(seasonId, raterId)` 按 `ratings` 现数出
`[{ value, quota, used, left }]`（只有 400/300/250 这三档）。**没有计数器列**，
好处是三个地方天然自洽：

- 改 `RATE_QUOTA` 对**正在进行的这期**立刻生效，不用数据迁移；
- 管理员在 `/admin` 的「打分记录」里清掉一条票 → **名额当场退回**，不用重启；
- **改分**（把一张 400 改成 50）→ 400 那档的名额当场回来，不用写任何"退名额"的代码；
- 开新一期 → 名额自动满血（统计是按 `season_id` 圈出来的）。

#### 两道关：服务端拦，前端提示

真正拦人的是 `routes/main.js` 的 `POST /entries/:id/rate`（灰按钮只是提示，
直接 POST 一个自己已经投满的档位照样被拒）。**改分走的是同一个地址**，所以这一道关
同样管着改分：把一张 50 改成 400，400 要是已经投满，照样被拒。
从 SELECT 到写库中间没有 `await`，better-sqlite3 又全是同步调用，
所以并发请求插不进这两步之间。

前端只做两件事，都在首页阵容墙（`views/partials/lineup-gallery.ejs`）：

1. 标题下面一行「本期你的打分名额：400 剩 1 · 300 已用完 · 250 剩 4（50 / 200 不限）」
   —— 名额是**投的人自己的**，不是被评分人的，所以在墙上说一次，不塞进每张卡里重复十几遍。
2. 投满的档位按钮 `disabled` 压暗、`title` 写着"本期的 400 名额已用完"。
   按钮**留着不移除**：五个格子是 `flex: 1 1 0` 等分整行的，抽掉一个剩下的会变形。
   **我占着的那一格例外**：它永远点得动（要能改分），高亮成"我打的"而不是压暗 ——
   灰掉自己那一票，等于告诉人"你这一票不算数"。

#### 老数据可能已经超额

名额是后加的规矩。规矩上线时有人手里已经投出去三个 400 —— 那些票**一张不动**
（票是成员对阵容的评价，新规矩不该回头改写已经投过的票），只是 `left` 归零：
**这期他不能再投 400**，其余档位照常。所以 `left` 是
`Math.max(0, quota - used)`，页面上显示"已用完"而不是负数。

### 五档从哪来

唯一真源是 `db.js` 的 `RATE_VALUES` —— 路由的校验、模板里的按钮都读它，
**改档位只改这一处**。同一段还有 `RATE_QUOTA`（每档每期的名额，见「每期名额」一节），
两处的键是同一套档位：**加档位要一起加**（`EYE_GAIN` 也是，那是第三处，见「慧眼等级」）。
打分截止的时点是另一组常数（`LOCK_WEEKDAY` / `LOCK_HOUR_BJ`），和档位无关，
见「打分截止」一节。

`schema.sql` 里**故意没给 `value` 加 CHECK**：档位是产品参数，多半还会调整，
而 SQLite 改 CHECK 要整表重建；上面 `entries` 的 R4 CHECK 守的是不变量
（分数/截图/时间三个字段同生共死），性质不同。唯一写入口是 `/entries/:id/rate`
这一个路由，校验就够。

### 均分 / 最高 / 最低怎么算

一期里所有打分**一次查回来**（`db.getSeasonRatings`），在 JS 里按 `entry_id` 归并
（`db.summarizeRatings`）—— 打分是「人数 × 阵容数」，量级很小，不值得写一堆
`GROUP BY` 再逐个回查打分人。

- **均分**保留 1 位小数（`233.3`）；正好是整数时 JS 直接打印成 `250`，不会出现 `250.0`。
- **最高/最低各只印并列里的第一个人**（`views/partials/name-list.ejs`，2026-10-14 改）。
  从前是"列前两个 + 等 N 人"，用户这天的要求是**只展示一个人、并且这一行必须只占一行**：
  卡片只有 228px 宽，「等 3 人」那半句一折行，同一排卡片的打分区就参差了（实测能折成三行，
  「人」字单独占一行）。
- 并列时**先投的排前面**（`db.getSeasonRatings` 是 `value DESC, created_at ASC`），
  所以印出来的是**第一个给出这个分的人**。**改分会刷新 `created_at`**，于是把票改成某档的人
  算"现在才给"、排在旧票后面 —— 这个顺序是对的，见「打分截止」最后一节。
  **库里返回的仍然是全部并列的人**（`db.summarizeRatings` 的 `maxBy`/`minBy`），
  砍掉的只是展示：谁先给的这一分是数据，不是版面。
- 打分人是纯文本，不做链接：卡片上已经有「昵称」和「图」两个链接了。
- 打分人昵称后面同样带慧眼等级圆框（2026-10-13 加）。名字 + 圆框顶到行尾时
  **被省略号切掉的是圆框**（`.rate-who` 是 `nowrap` + `text-overflow: ellipsis`），
  名字永远完整 —— 12 字昵称（注册上限）加圆框在 202px 的行里放不下，这是有意的取舍。
  （2026-10-16 之前手机那档还有一段"四处各收一点点"的补丁：两列 150px 的卡里那一行只有
  135px，5 个字的名字加圆框要溢出 7px。改成一行一张的横排卡之后打分区通栏了、
  手机上比桌面还宽裕，**那段补丁整段删了**。）

汇总的 `viewerId` 一路传进 `db.getLineupWall(seasonId, viewerId)`，用来认出
「我投的是哪一档」。

### 只显示在首页阵容墙

`/seasons/:id` 没动。所以**新一期开始后，上一期的阵容墙就从首页消失了**，
那些均分要在「我的打分记录」里才翻得到。

### 点错了怎么办

**截止前自己改**：阵容墙上点别的档位就改了（见「怎么投」），不用找人，也不占额外名额 ——
原来那档的名额会当场退回来。
**过了截止**就只剩管理员的出口：`/admin` 的**「打分记录」**（默认用 `<details>`
收起），列出**进行中那一期的全部打分**，每条一个【清除】。清掉之后那个阵容对
这个人重新变成「没打过」，名额也当场退回；不过**过了截止本人也不能重投**，
所以这一下是"撤掉那条票"，不是"给他一次重投的机会"（提示语里分了这两种情况）。

只列进行中的期就够：打分只能在进行中的期产生，**要清历史期的先【撤销结算】**，
那一期就成了进行中的期，记录自然出现在这儿。

### 整期清空（`/admin` 的【清空本期全部打分】）

逐条删适合"撤掉某一条"，整轮投乱了、想让大家重投一轮时用批量那个：
同一张卡片的表格**底下**一个【清空本期全部打分（N 条）】，一次清干净
（`db.clearSeasonRatings`，就一条 `DELETE … WHERE entry_id IN (SELECT id FROM entries WHERE season_id=?)`）。
几处有意这么定：

- **只清进行中的期**，已结算的拒掉并指路【撤销结算】。已结算期的记录看着"没用"
  （名次早定了），其实慧眼等级就是拿它算出来并落库的（`eye_adjustments`）——
  这时删记录**退不回等级**，只会让两边对不上；那份记录本身也是"当时谁投了谁"的痕迹。
- **按 `:id` 圈定赛期**，不是"清当前进行中的那一期"：从渲染管理页到点下按钮之间，
  赛期可能被别处结算 / 撤销结算，带 id 才能保证清的是屏幕上写的那一期。
- **按钮摆在表格下面**，不挨着几十个逐条【清除】：这是这一页唯一不可逆的批量操作，
  离手滑越远越好，顺带让人先把名单扫过一遍。
- **有票才渲染**。一条票都没有时那一段是"这一期还没有人打分"，路由那边还兜着：
  真撞上 `n = 0` 回一句「本来就没有打分记录」，而且走 `err` 不走 `ok` ——
  绿条是"干了件事"的意思，这里什么都没干（按钮不出，能撞见这条的多半是手打地址）。
- **名额当场全满血**：名额是现数的（见「名额不落库，每次现数」），清空不碰任何计数器，
  删完 `db.getMyQuota` 自然回到 2 / 3 / 4。
- **提示分两种情况**，和逐条删同一个口径：没过截止说"大家都可以重新投"，过了截止说
  "谁都不能重投了"。批量删更容易忘掉这件事，所以确认框和绿条里各写了一遍。
- **只有 POST，没有 GET**：GET 打这个地址是 404。清库这种事不该能靠点开一个链接触发。
- 顺带一提，这个按钮**不碰慧眼等级**：等级只在结算那一刻算，见「慧眼等级」一节。

**管理页的确认框从这版起统一走 `data-confirm` + 页脚一段脚本**，不再写
`onsubmit="return confirm('…把昵称拼进来…')"`。原因不是风格：昵称是成员自己起的
（1–12 个字，什么字符都行），模板把 `'` 转义成 `&#39;` 之后，浏览器解析属性时
**又会还原成 `'`** —— 那个引号能从 JS 字符串里跑出来执行（管理页里的存储型 XSS）。
`data-confirm` 读出来只是数据，没有这个问题。
（`/score` 里那句是纯静态文案、不含任何用户输入，留在 `onsubmit` 里没动。）

**踩过的坑**：`views/admin.ejs` 的页脚脚本里，注释写到了"不要用 `onsubmit` + 模板标记"
这句，于是注释里出现了一个 EJS 开始标记 —— **EJS 会求值模板里任何位置的标记，
注释里也一样**，直接 `ReferenceError: 昵称 is not defined`，整个 `/admin` 400。
写模板注释放不下这个标记时，用文字描述（"EJS 的开始标记"）绕开。

### 样式上的两个坑（都是实测出来的）

1. **`.rate-k` 不能用 flex 的定宽基准。** 一开始写的 `flex: 0 0 2em`，
   而 2 个汉字在 0.72rem 下正好等于 2em —— 差一点点就折成「均」/「分」两行。
   改成 `flex: 0 0 auto` 交给 max-content：三个标签都是 2 个字，宽度自然一样，
   数字照样对齐。
2. **打分人那一串用 `white-space: nowrap`，配 `.rate-line { flex-wrap: wrap }`。**
   否则 `overflow-wrap: anywhere` 会把「张三、李四」从中间劈成
   「张三、李」/「四」。nowrap 之后它作为一个整体换行：装得下就留在同一行，
   装不下就整段下移一行。

另外注意 **Pico v2 的根字号是响应式的**：≥1280px 时 `1rem = 20px`（125%），
窄屏才是 16px。同一个 `0.7rem` 在桌面和手机上差 25%，量尺寸时别忘了。

## 慧眼等级

**所有人初始 10 级**（`users.eye_level` 的 DEFAULT），**只在每期结算那一刻**动，
而且只动**给本期积分第一 / 第二的人打过分的**那几个人 —— 奖励的是"看准了冠军"的眼光，
不是按人头普涨。没给前两名打过分的人、这期压根没参加的人，等级一动不动。

**只涨不跌**（2026-10-13 起）：低分档不再扣等级，见下面的档位表。所以
`users.eye_level` 一旦涨上去就是"资历"，除了【撤销结算】没人能让它回头。

### 档位表

**给积分第一和第二的人打分是同一张表**（2026-10-13 起，第二名原本要减半）：

| 你打的 | 400 | 300 | 250 | 200 | 50 |
|---|---|---|---|---|---|
| 等级 | **+3** | +2 | +1 | 0 | 0 |

名次只影响"算不算"：**只认前两名**，给第三名往后的人打分**一分不加**（这是有意的，
不然等于按人头普涨）。前两名之间不再有别 —— 看准第二名和看准第一名一样值钱。

**50 和 200 不涨也不跌**（2026-10-13 起；原本是 −2 / −1）：打低分的意思是"我觉得他
这套打得一般"，不该倒扣眼光。于是整张表**只有正的**，慧眼等级**只涨不跌** ——
初始那 10 级就是地板。这两个档位在 `EYE_GAIN` 里**留着键并显式写 0**，不是漏掉了。

一个人一期里的多张票**先加起来再落账**（既给第一打了 400、又给第二打了 250 → 净 +4）。
加完是 0 的（只给前两名打了 50 / 200）**不记档、不写明细** ——
这人连"变动 0"这一行都不会出现在变动榜里。

**自评也算**：本站不禁止给自己打分（见上面「五条硬规矩」），自评的票一样进这张表 ——
真给自己打个 400 又恰好拿了第一，就是实打实的 +3。

### 什么时候算

只有**结算**（`/admin` 的【结束本期】）会算，而且和名次在**同一个事务里**定下来
（`db.settleSeason` → `applyEye`）。所以在进行中的期里看到的等级，
反映的是**上一次结算之后**的状态。

算的是**结算那一刻库里的票** —— 打分的截止点（每期开期后第一个周四 12:00）就是为了
让这些票在名次明朗之前就定下来，见「打分截止」一节；**改过分的票按改完的值算**，
因为改分是 `UPDATE` 那一行，不是新插一条。

结算完管理页的绿条会把变动念一遍（"慧眼等级：张三 +3、李四 +1"）——
否则有人发现自己的等级变了，在页面上找不到任何解释。

### 撤销结算 / 删赛期会退回去

`eye_adjustments` 一期一人一行，存在的唯一目的就是**能原样退回**：

- 【撤销结算】→ 逐条减回去、明细清空（`db.revertEye`，被 `db.reopenSeason` 调用）。
- 【删除赛期】→ 先退回等级再删（`routes/admin.js`）。已结算的期删掉就当从没办过，
  不留白拿的等级；`eye_adjustments` 随 `seasons` 级联删，所以顺序必须是"先退、再删"。
- 【结束本期】自己也会**先退一次再算**（`db.settleSeason` 里 `applyEye` 前那句 `revertEye`）。
  正常流程走不到那句（结算前必然是 open 期，而变回 open 只能经 `reopenSeason`，那里已经退过），
  但少了它，万一哪条路径漏了退，同一期再算一次就会撞 `UNIQUE(season_id, user_id)`
  把整个结算回滚掉、管理页弹个错。加上之后结算是**幂等**的：算两遍结果一样。

不退的话「撤销 → 重新结算」会把同一期**累加两次**。这也是等级做成
"加在 `users.eye_level` 上的累计值 + 一张明细表"、而不是每次重算的原因。

### 昵称旁的小圆框

昵称（id）旁边的**小圆框**，实现是 `views/partials/eye.ejs` + `app.js` 的 `eyeLevel(uid)`：

- **颜色按等级分四档**（2026-10-13 改；档位由 `app.js` 的 `eyeTier` 判，配色在
  `style.css` 的 `.eye-*`）：**越往上越亮** —— "亮"就是直接用色板上那支亮色再垫一层同色底，
  不靠发光 / 投影那些特效（圈只有 1.5em，加了反而抢注意力）。

  | 等级 | 10–11 | 12–14 | 15–19 | 20 及以上 |
  |---|---|---|---|---|
  | 颜色 | **暗**（暖灰，初始等级的样子） | 亮银 | 亮蓝 | 亮金 |

  颜色是唯一的等级信号，所以圈做得很小（约 1.5em），不跟昵称抢注意力；
  鼠标停上去有 `title`。结算只涨不跌，所以低档实际上只有初始的 10 和刚涨 1 级的 11；
  形状和颜色**分开写**（`.eye` 只管盒子，`.eye-dim` 和它同组选择器），
  于是模板万一漏了档位类会落到暗色，不会变成一个没颜色的裸圈。
  两个色号是复用的：亮银 / 亮蓝就是阵容卡上"上期第二 / 上期第一"那两条描边用的令牌，
  金属感是同一套语言。
- 等级是**每次请求现查的一张 uid → 等级 小表**（`db.getEyeLevels`），
  而不是给十几处 SQL 各补一列 JOIN。成员就十几个人，这点开销换的是
  "昵称出现在哪、圆框就跟到哪"，一处不漏：

  | 页面 / 位置 | 谁 |
  |---|---|
  | 首页的排名表（只在回退分支，见「首页看板」）、赛期详情的战绩卡 | 每位参赛者 |
  | 首页/赛期详情的「还没交积分」名单 | 每个人 |
  | 阵容卡（首页阵容墙） | 卡主，**以及打分区「最高 / 最低」里印出来的那个打分人**（并列的其余人不印，见上） |
  | 总排行榜 `/rank` | 每个人 |
  | 个人页标题、改密码页的「当前身份」 | 本人 |
  | 管理页（成员表、赛期表的**胜者**列、打分记录的**打给谁 / 打分人**两列） | 相应的人 |
  | 打分记录 `/ratings`、历史赛期的胜者列、慧眼变动榜 | 相应的人 |

- 查不到这个人时**整个不输出**圆框 —— 宁可少一个，也不要在页面上留个空圈。
- 和它**正好相反**的是「演武王 / 慧眼王」那两枚称号章（下一节）：那个只在阵容墙上、
  跟着卡走，别的页面一律不挂。两者不是一套东西，别顺手把称号也加到上表那十几处去。

**有几处是套不上圆框的**：`<img alt="张三 的阵容截图">`、按钮的 `aria-label`、
`onsubmit="confirm('重置 张三 的密码？')"` 这类**属性里的昵称**，个人页的浏览器标签
题目（`<title>张三 的战绩</title>`），以及管理页结算后的绿色提示条
（`<%= flash.msg %>` 是转义的，故意不放开 HTML，免得昵称成了注入口）。
这些地方要么是给读屏/弹窗/标签页看的纯文本，要么是转义输出，塞不进一个 `<span>`。
真要看等级，同一页上同一行旁边就有。

**打分人那个名字**走 `views/partials/name-list.ejs`：它拼的是一个「昵称 + 圆框」，
而不是从前的 `nameList` 助手那样先 join 成一个字符串（字符串里塞不进标签）。
并列的其余人**不印**（库里照样全给，见「均分 / 最高 / 最低怎么算」），
所以那一行现在就是一个名字，`.rate-line` 因此改成了 `flex-wrap: nowrap` ——
挤不下时省略号切的是圆框，不是把名字折到下一行去。

`views/partials/lineup-gallery.ejs` 里引它写的是 `include('./eye')` 而不是 `'partials/eye'`：
EJS 解析 include 时**先相对本文件**（→ `views/partials/partials/eye`，不存在），再退回 views 根，
而退回那步要靠 Express 传进来的 `views` 选项 —— 写同级路径，两个入口（Express / 裸 ejs）都对。
`name-list.ejs` 引 `./eye` 同理。

⚠️ **别在 EJS 注释里写出标签本身**（哪怕只是举例）——注释是遇到第一个收尾标签就结束的，
写在里面的标签字样会把注释提前截断，后半段注释当正文吐到页面上。这一条是实测踩出来的：
`views/partials/name-list.ejs` 的注释里写了半截注释标签，页面上就多出一行说明文字。

### 本期变动排行榜

**目标就一个：一眼找出这期慧眼涨得最多的人。** 实现是 `views/partials/eye-board.ejs`，
两处引它，都只在**已结算**的期里出现：

| 页面 | 位置 | 标题 |
|---|---|---|
| `/seasons/:id`（已结算） | **战绩卡上面**（不是下面） | 本期慧眼等级变动 |
| 首页回退到「上一期结果」时 | 排名表 / 阵容墙后面 | `<期名> 慧眼等级变动` |

- 数据就是 `db.getEyeAdjustments`（按 `delta` 降序、并列按 `users.id`），**第一行就是答案**。
  只有给积分第一/第二打过分的成员才在表里，净增减为 0 的压根不写记录。
- 第一行挂一枚「本期涨得最多」，但**只在 `delta > 0` 时挂**。2026-10-13 起写进表里的行
  必然是正的，所以这句现在永远成立 —— 留着是防"旧规则时代结算过、之后没重新结算"的
  负数明细：那种情况下第一行只是"跌得最少"，挂那句话就是撒谎。
- 涨用亮蓝、跌用暗红（`.delta-up` / `.delta-down`），和圆框的颜色语义对齐 ——
  同一屏里两个颜色应该指的是同一件事。低分档不再扣等级之后**新结算出来的只有涨**，
  `.delta-down` 同样只服务旧明细。
- **空表也照常出标题 + 一句说明**（"本期结算时没有人的票能加等级（给积分第一/第二的人
  打 250 分以上才算），所以慧眼等级全员没变"）：空表有两种成因 —— 压根没人给前两名打分，
  或者打了但都是 50 / 200 这种不加等级的档。"为什么大家等级都没变"本身就是要回答的问题，
  静悄悄什么都不显示反而让人以为坏了。
- 榜里昵称旁那个圆框是这个人**现在**的等级，不是这一期结束时的。跨了几期之后两者会不一样，
  所以表格底下专门写了一句，免得有人拿它当"结算后等级"来对账。

### 改规则要动哪

`db.js` 的 `EYE_GAIN` 是**唯一真源**，整站就这一张表 —— 改档位只改这一处。
（2026-10-13 之前还有第二张"减半向零取整"的表，由 `Math.trunc(base / 2)` 推出来；
前两名合并成同一张之后，`db.eyeDelta` 连 `rank` 参数都去掉了。）
⚠️ `EYE_GAIN` 的键就是 `RATE_VALUES` 的五个档位，**改档位时这两处必须一起改**；
对不上的档位按 0 处理（不涨不跌、不写明细），老数据里已下线的档位就靠这条兜底。

⚠️ **50 / 200 现在是有意写 0 的**（键留着，不是漏了）。要恢复"打低分倒扣"，把这两个值
改回负数就行 —— 但要注意**已经结算过的期不会回头重算**（等级是 `users.eye_level` 上的
累计值，明细也只记当时的 `delta`），改规则只影响之后的结算。真要追溯，只能对那几期
【撤销结算】再【结束本期】。

### 老库怎么补上这一列

`schema.sql` 里全是 `CREATE TABLE IF NOT EXISTS` —— 对**已经存在**的表一个字都不会改，
所以 `users.eye_level` 是 `db.js` 顶部一段**幂等迁移**补的：`PRAGMA table_info(users)`
看一眼列在不在，不在就 `ALTER TABLE ADD COLUMN`。跑多少次都无所谓，新库建表时已经带上了。
以后再加列，也走这一段。

## 结算与排行（积分 → 名次 → 胜场 → 胜率）

2026-10-15 用户把这一整条链的口径改了一遍。三条规矩，一起看才说得通：

| # | 规矩 | 从前是什么样 |
|---|---|---|
| 1 | **只要上传了阵容就算参与本期**（交过积分当然也算） | 只有交了积分才算参赛 |
| 2 | **每期积分前两名都算胜利**（`db.TOP_N = 2`） | 只有第一名算胜者 |
| 3 | 排行榜**先比胜场、再比胜率，两样都一样时先加入的在前** | 中间还插着一个"场次多者在前" |

### 参赛 ≠ 交分，两个数别混用

一期里每人一条 `entries`（`UNIQUE(season_id, user_id)`），**上传阵容**和**录积分**都可能
先把这条建出来，所以"参过几期"和"交过几次分"是两件事，各有一个函数：

| 数 | 怎么算 | 谁在用 |
|---|---|---|
| `db.countPlayers` | 有阵容图**或**有积分 | `/rank` 的分母（胜率）、赛期页/历史页/管理页的「参赛 N 人」、战报首行 |
| `db.countScored` | 有积分 | 结算的前置条件（少于 2 人不能结算）、赛期页的「交分 M 人」、战报首行第二个数 |

分数那三列（平均分 / 最高分 / 最佳名次）**只认交过积分的期**：`AVG` / `MAX` 天然跳过 NULL，
只传阵容没录分的人这三格是空的，模板一律印「—」（不是 0，也不是留白）。
"只传了阵容、传也没传分也没交"的空 entry（点进 `/lineup` 就建出来了那种）**两边都不算**。

这一条改了以后，`/rank` 上从"只列交过分的三五个人"变成"**列全部到过场的人**"——
2026-10-15 的第 1 期实测：21 人传了阵容、3 人交了分，榜上因此是 21 行。

### 名次与胜者

- **名次**（`entries.final_rank`）永远只看积分：`积分降序 → 提交时间升序 → id 升序`（R2 没动）。
- **胜者**（`entries.is_winner`）是**前两名**（`db.TOP_N`）。结算时一次写两列，
  见 `db.settleSeason`；胜场统计直接读 `SUM(is_winner)`，所以重算一遍数字立刻跟上。
- `TOP_N` **只有一处定义**，三件事共用它：谁算赢（`settleSeason`）、结算时给谁打的票能涨
  慧眼等级（`applyEye`）、阵容墙上给上一期前两名描边（`getPrevAces`）。它们都是"积分前两名"
  这同一个概念，故意绑在一起；哪天要拆（比如"前三名都算赢、慧眼还是只看前两名"），
  把这个常数拆成两个，别在调用处各写一个字面量。
- 页面上跟着改的地方：赛期详情的战绩卡（两张卡都描金边、都挂「👑 胜者」）、首页回退分支
  那张结果表（两行 `.row-first`）、历史列表的胜者列（**一格列两个人**）、管理页的胜者列。
  ⚠️ `db.getHistory` 因此**不能再写成 `LEFT JOIN … AND e.is_winner=1`**：那在"一期只有一个
  胜者"的年代是一行，改成两名胜者之后同一个赛期会在列表里**出现两行**。现在改成两条查询 +
  在 JS 里归并，`winners` 是一个数组（冠军在前）。

### 排行榜怎么排（`db.getRankBoard`）

```
ORDER BY wins DESC, win_rate DESC, avg_score DESC, joined_at ASC, u.id ASC
```

- **`plays DESC` 已经拿掉**（2026-10-15）：它其实几乎从不生效 —— 胜场相同时"胜率也一样"
  基本就意味着场次一样（胜率 = 胜场 / 场次），只有四舍五入到同一位小数时才轮得到它。
  留着只会让人以为"多打几场"是个优势。
- **第三条是平均分**（2026-10-16 用户加的），排在时间前面：读的就是页面上那一列
  （只算交过积分的期）。只传阵容、一场没交分的人这一列是空的，`avg_score DESC` 在 SQLite
  里把 NULL 排在最后，正好是"没分的人垫底"。⚠️ 它**只决定并列的人之间谁在前**（以及那枚
  演武王章挂在谁身上），**不进称号的判据** —— 演武王仍然是"胜场最多的人里胜率最高的"，
  墙上并列的照样各戴一枚。
- **`joined_at` 就是 `users.created_at`**（加入时间，个人页上印的"加入于"）。
  全库只有这一个每人一份的时间，先来后到也说得清。
- 末尾的 `u.id` 只是兜底：**保证顺序是全序**，同一毫秒注册的两个人不能靠引擎的脾气决定谁在上面。
- 排行榜**第一行**那枚章 2026-10-15 起从「头名」改名成「**演武王**」，和阵容墙上那枚朱红章
  是同一件事、判据也一样。⚠️ 两处的"并列"处理不同、都是老规矩：墙上**并列一起封**
  （胜场和胜率都一样的人各戴一枚），榜单**只给第一行挂**（第一行只有一位，由平均分和加入时间定）。
  于是**可能同时有好几位演武王**，而榜上的章只出现在最上面那一位身上 —— 要改成"只封一位"
  就动 `db.getTitles`。

### 这一页的文案也是判据的一部分

`/rank` 的页头、`/history`、`/seasons/:id`、首页几个提示（"你本期传了阵容但还没录积分…"、
"没交积分就拿不到名次…"）都写着上面这三条。改规矩时**这些句子要一起改** ——
它们是成员唯一能自己核对的地方，说法和数据不一致比数字错了更让人困惑。

### 改了规矩怎么修历史数据

`settleSeason` 是幂等的（先把这一期的名次明细退回、再按当前票重算一遍），所以给老数据
补第二名胜者只要**再结算一次**。日常流程是 `/admin` 的【撤销结算】+【结束本期】，
但那条路会把期变回进行中、`settled_at` 也会刷新；只想修正数字时用本机那个小工具：

```bash

node .devlocal/resettle.js                 # 开发库：所有已结算的期
node .devlocal/resettle.js 1               # 只重算第 1 期
YANWU_DIR=/home/raving/work/sanmouyanwu node .devlocal/resettle.js   # 对着线上库跑
```

它保留 `settled_at`、不动 `status`，跑完会把每一期"改前 / 改后"的名字打出来。
**2026-10-15 就是这么修的第 1 期**：路飞王 84 第一、动力强劲 76 第二，后者补上了胜者那一笔
（`is_winner` 0 → 1；慧眼等级、`settled_at` 一个字没动）。

## 称号（演武王 / 慧眼王）

阵容墙的卡片上，昵称**前面**可能多出两枚章（2026-10-14 加）：

| 称号 | 谁戴 | 颜色 |
|---|---|---|
| **演武王** | **胜场最多的人里，胜率最高的**那批（并列就一起封） | 朱红 |
| **慧眼王** | **慧眼等级最高的**那批（并列一起封） | 亮蓝 |

鼠标停上去有提示，写着这一枚是怎么来的（几胜几场、胜率多少 / 几级）——
光看"演武王"三个字没人知道凭什么，而称号是给人争的，判据得能当场查出来。

### 演武王：先比胜场，再比胜率

判据就是 `/rank` 排序的前两项（`wins DESC, win_rate DESC`），所以**第一行必定是演武王**，
两个页面对得上（`/rank` 第一行那枚章 2026-10-15 起印的就是这三个字，从前写的是「头名」）。
反过来"只看胜率"是不行的：只打过一期、恰好赢了一次的人是 100%，按胜率就该他称王 ——
而他在排行榜上连第一行都不是。**先比胜场**把这种情况挡在外面：赢的次数不够，胜率再漂亮也不封。

并列的**全都封**（这是用户定的）：例如两人都是 2 胜 / 4 场，两枚章都出。
⚠️ 但**排行榜只给第一行挂章**：排序的第三条判据（先加入的在前）会在并列的人里定出唯一一位，
章落在他身上，其余并列的人只在阵容墙上戴章。要改成"只封一位"，改 `db.getTitles` 的判据。

⚠️ **胜场为 0 时一个都不封**。全站都没人赢过的时候，"胜场最多"就是 0 胜，那批人的胜率也全是 0 ——
不拦这一下，所有没赢过的人当场都成了演武王。

口径和 `/rank` 完全共用一个查询（`db.js` 的 `STATS_SQL`）：**只算已结算的期**，
**上传了阵容就算参赛**（2026-10-15 起；从前要交过积分才算）。只传阵容没录分的人照样进榜、
照样算在胜率的分母里 —— 但他这期 0 胜，除非赢了才封王。

### 慧眼王：等级最高的那批，但没人涨过就不封

等级本身怎么算见上一节（结算时按"有没有看准前两名"加，只涨不跌）。称号只挑**最高的那一档**，
并列的全给。**只有一条额外规矩：最高等级还停在初始 10 级时，谁都不封。**

不给这条规矩的话，严格按"同级都封"就是开局全员戴冠（所有人初始都是 10 级）——
一个所有人都有、且一时半会儿掉不下去的称号等于没有称号。第一次结算把谁顶到 11 级之后，
王冠自己就出现了；之后随着等级拉开，戴的人会自然收窄到真·最高的那几个。

### 只在阵容墙，而且跟着卡走

**全站只有阵容墙挂这两枚章**（`views/partials/lineup-gallery.ejs`，首页本期和"上一期结果"
两条分支共用同一个 partial，所以两条分支都有）。这是用户定的显示范围：称号是排面，
阵容墙是唯一"看排面"的地方；排行榜、排名表、个人页那些地方昵称旁边已经有慧眼圆框了，
再挂两枚章会把 228px 的卡和别人家的表格都挤乱。

所以它和慧眼圆框正好相反 —— 圆框是"昵称出现在哪就跟到哪"，称号是"只在墙上，
而且**跟着卡走**"：这个人在这一期没传阵容（墙上没他的卡），称号也就不出现，
哪怕他是实打实的演武王。他传了阵容的期里自然就有了。

也没有"称号榜"这一页：想看完整的胜率/等级，去 `/rank` 和个人页，那里的数字就是判据本身。

### 称号不落库

`db.getTitles()` 每次请求现算（榜单一次 `GROUP BY` + 一眼 `MAX(eye_level)`），
**库里既没有"称号"这一列，也没有称号表**。存下来就得在结算、【撤销结算】、【删除赛期】、
清空整期打分……每一条会影响榜单的路径上记得同步改一遍，漏一条就会出现
"榜上第一换了人、王冠还戴在别人头上"。现算的代价是两条小查询（成员就十几个人），
换来的是它永远不会和 `/rank` 对不上。

同理，**撤销结算之后等级退回去，慧眼王跟着就没**（不是"曾经当过就永久保留"）——
这两枚章描述的是**此刻**的第一名，不是荣誉记录。

**不排除已禁用的成员**：胜场和等级都照 `/rank` 与 `users` 表原样算。称号一旦和榜单分家
（"排行榜第一"和"演武王"是两个人），就会有人拿着两个页面对不上。

### 实现在哪

| 东西 | 位置 |
|---|---|

## 阵容卡的上期名次描边

首页**阵容墙**上，**上一期**积分第一的阵容卡描**亮蓝**边、积分第二的描**亮银**边
（2026-10-13 加）。它给的是"上期打出来的名次"，所以和卡上那个 `#N`（**本期**积分名次）
完全是两回事：一个看你上期第几，一个看你本期第几。

| 谁的卡 | 边 | 类名 |
|---|---|---|
| 上一期积分第一 | 亮蓝 `#79c2f2` | `.shot-card.is-prev-first` |
| 上一期积分第二 | 亮银 `#ccd6e2` | `.shot-card.is-prev-second` |

- 「上一期」= 这一期之前**最近一个已结算的期**（`db.getPrevAces`，名次取 `final_rank`，
  它是结算时定死的）。没有就一条边都不描 —— 第一期、上一期还没结算、
  或者上一期刚被【撤销结算】（此时它变回进行中，"上一期"就不存在了），都属于这种。
- 谁在墙上得先**传了阵容**：上期第一这一期没传图，墙上没他的卡，自然也没有边，不会出错。
- **为什么不用 `border-width: 2px`**：`.shot-card` 宽度写死 228px，框里的图也是写死 226×181，
  边框加粗会挤掉内容宽度、让 `overflow: hidden` 从图上多裁一圈。所以"亮"是
  **边框本身换成亮色 + 外面补一圈 `box-shadow: 0 0 0 1px` 的环和一点辉光** ——
  阴影不参与布局，加多少都不动卡片尺寸，也不会裁到图。
- 光看蓝边银边猜不出含义，所以阵容墙那段说明文字里**会多出一句图例**
  （`rows.some(r => r.ace)` 才出，没人描边时那句不存在），卡上另有 `title="上期积分第一"` 悬停提示。
- **只在首页阵容墙**。`/seasons/:id` 的战绩卡不描：那一页本来就在展示"这一期"的名次，
  再描一圈"上期第几"两套名次容易看串。

## 游客模式（没登录的人能看什么）

2026-10-14 加。在这之前**整站都要登录**（`routes/main.js` 整条挂在 `requireLogin` 后面），
没账号的人连阵容墙都打不开。现在开了一个只读入口：**看阵容墙 + 在每套阵容下面留一句话**。

| 谁能看什么 | 游客（没登录） | 成员 |
|---|---|---|
| 阵容墙：阵容图、阵容说明、称号章、上期名次描边、互评均分/最高/最低、评论 | ✅ | ✅ |
| 卡顶栏的积分（`4800 分` / `未交积分`） | ❌ 整个不渲染 | ✅ |
| 卡上的 `#N` 积分名次 | ✅（口径是"不给积分"，不是"不给名次"） | ✅ |
| 排名表、赛期详情（积分截图挂在那儿）、"还没交积分"名单、成员页、历史、总排行 | ❌ 跳登录 | ✅ |
| 上传阵容、录积分、打分 | ❌ | ✅ |
| 发评论 | ✅ 署名统一「游客」 | ✅ 署名自己的昵称 |

- **入口是 `/wall`**，`GET /` 对没登录的人 302 到它。之所以让首页改道、而不是往
  `views/home.ejs` 里塞一个游客分支：那一页 189 行、两个大分支（本期看板 / 上一期结果），
  塞进去等于把每个 `if` 都加一遍条件。改道之后首页模板**一行都不用动**，
  游客还白得一个能转发的固定地址。
- 成员访问 `/wall` 是**允许**的（一律 `canRate:false`，不出打分按钮）——这样管理员想核对
  "外人看到的是什么样"，不用退出登录也不用开无痕窗口。游客那版和成员那版只差三处：
  打分按钮、卡上的积分、昵称是不是链接（游客点个人页只会跳登录，所以给他纯文字）。
- 没有进行中的期时，`/wall` 摆**最近一个已结算期**的阵容墙（和首页回退分支同一个口径）；
  一期都没办过就只出一句空态。

### 图片：所有图现在都公开（2026-10-15 的取舍）

**这一节整个换了。** 从前这里是全站最绕的一处：阵容图和积分截图物理同层、URL 上分不出谁
是谁，所以 `app.js` 里挂了一个 `canSeeUpload` 中间件**逐文件查库** ——
登录的人全放行，游客的请求要命中 `lineup_images.filename` 才放行，否则 404
（不是 403，403 等于确认"这里确实有一张积分截图"）。改造之后：

- **图片在 R2 上，是公开可读的**。桶不开签名（页面里直接写域名），所以
  **积分截图也不再要求登录** —— 从前游客取它会拿到 404，现在照样 200。
- `app.js` 的 `canSeeUpload` / `noImage` / `ensureThumb` 三个中间件、以及整块
  `/uploads` 静态挂载**全删了**。`db.isLineupImage`（从前那条白名单的判据）
  成了没人调的死代码；真正在用的是新加的 `db.isImageInUse` —— 提交阵容时用它挡
  "同一张图被两行引用"（见 `routes/main.js`），那是数据完整性，与鉴权无关。
  `/uploads/:name` 现在只剩一条**老链接的 302 跳板**（`routes/uploads.js`）。

**为什么可以这样**（这是用户拍板的一条取舍，不是疏忽）：

- 文件名是 `randomUUID()`，**猜不到**，所以不是"全网可枚举"——别人得先拿到链接。
- 而链接本身就是公开的：阵容墙上每张卡的 `href` 就写着它，游客可见。
- 代价是**一旦有人把链接转出去，它就永久有效**（对象上还盖着一年 immutable），
  而且**积分截图现在也在其中**。这条取舍换来的是"服务端不碰字节"这个架构上的大简化，
  以及上传路径彻底绕开那条慢隧道。

> 老链接没断：`/uploads/<名字>` 在 Node 里 302 到图床域名（严格 UUID 形状才跳，
> 其余一律 404 —— 不做成"以 `/uploads/` 开头就弹走"那种半开放的跳转口）。
> 路径穿越（`/uploads/%2e%2e%2f.env`）、目录（`/uploads/`）、多一层
> （`/uploads/.incoming/x.jpg`）都落在末尾那个 404 兜底上 —— **那个兜底不能省**：
> 少了它，这些路径会**穿过这个路由**一路抵达后面的 `requireLogin`，
> 游客拿到的是一张"跳登录页"而不是 404（`routes/uploads.js` 末尾的注释记着这件事）。

## 反爬虫（2026-10-15 加）

起因是图片搬到 R2 之后**全部公开**（见上一节），而全站**一个有效的 robots.txt 都没有**。
实测三条入口当时是：

| 入口 | 那时 `/robots.txt` 返回什么 | 等于 |
|---|---|---|
| `www.raving-hash.top`（过 Cloudflare） | **302 → /login** | 爬虫拿不到规则 ⇒ 默认全允许 |
| `mmm.raving-hash.top:18080`（直连，不过 Cloudflare） | 同上（同一个 Node 进程） | 同上 |
| `img.raving-hash.top`（R2 图床） | 200，但正文是 Cloudflare 自动注入的 1248 字节**纯注释**，一条指令都没有 | 没有 `User-agent` 组 ⇒ 没有规则 ⇒ 默认全允许 |

### ★ robots.txt 是按 origin 各管各的

这是最容易搞错的一点：协议规定 **scheme + host + port** 才算一个 origin，
robots.txt 只管自己那个 origin。所以本站的爬虫策略**天然是两份**，写一份管不了另一个：

| | 站点 | 图床 |
|---|---|---|
| 放哪 | 一个普通的 Express 路由（`routes/public.js` 的 `GET /robots.txt`） | **R2 桶里的一个对象**（图床前面没有 nginx，也不经过本站进程） |
| 怎么装 | 跟着代码发布走 | `node --env-file=.env scripts/put-robots.js`（**仓库之外的状态**，见 `deploy/DEPLOY.md`） |
| 正文 | `robots.js` 的 `SITE` | `robots.js` 的 `IMAGE` |

两个页面入口（80 隧道 / 18080 直连）共用同一个 Node 进程，所以**一份就够**。

> ⚠️ **`GET /robots.txt` 必须挂在 `requireLogin` 之前**（它现在在 `routes/public.js` 里，
> 而那个文件正挂在前面）。挂到后面会变成 302 到 /login —— 而爬虫拿不到 robots.txt 时
> 的默认是"全允许"（RFC 9309：4xx 视为无限制），那正是上面表格里那个坏状态，
> 等于这份文件白写。`test-guest.js` 专门盯着这条。

### 两份的口径**故意相反**

站点**放行搜索引擎、挡掉 AI 爬虫**；图床**一律不爬**。
「站点能搜到」不等于「成员那 54 张原图该进图片搜索」—— 图片一旦被收录就会被缓存住、
撤不回来（`deploy/DEPLOY.md`「安全提醒」第 4 条讲的就是这件事）。
所以 `robots.js` 里是两段**不一样的**正文，别为了"统一"把它们合并。
`test-guest.js` 里有两条断言分别锁住这两份的相反口径。

AI 爬虫名单按 2026 年的三个档次分组（`robots.js` 里逐条列出了）：
训练类（`GPTBot`/`ClaudeBot`/`CCBot`/`Bytespider`…）、AI 搜索类（`OAI-SearchBot`/`PerplexityBot`…）、
用户触发类（`ChatGPT-User`/`Claude-User`…）。

> ★ `Google-Extended` 与 `Applebot-Extended` **只写在 robots.txt 里**，nginx 的 `map` 里没有：
> 它们是 robots.txt 专用的"训练开关"，**不是会出现在日志里的 UA**（真身是
> `Googlebot`/`Applebot`），放 `map` 里永远匹配不上。反过来也不能拿这两个词去拦
> `Googlebot` —— 那就把搜索引擎一起挡了。

### 执行层：nginx 侧

robots.txt 只是**声明**（RFC 9309 是自愿遵守的），不守规矩的爬虫根本不看。
所以同一套口径在 nginx 里再做一遍，配置在 `deploy/nginx-yanwu.conf`：

- `map $http_user_agent $ai_bot { … }` + `if ($ai_bot) { return 403; }` —— 命中的 AI 爬虫
  连 Node 都不进。名单与 `robots.js` 一致，但**没有**上面那两个"开关"。
  ★ `nginx` 侧刻意**没有** `Googlebot` / `Bingbot` / `Baiduspider` / `PetalBot`
  （PetalBot 是华为的搜索引擎爬虫，不是 AI）—— 顺手把"像爬虫的"一起拦掉等于换了条口径。
- `limit_req` 洪水保护。取值**故意很松**：经 Cloudflare 那条入口，nginx 还原出来的
  `$remote_addr` 到底是真实用户还是 **CF 边缘 IP** 还没实测过；若是边缘 IP，则同一片边缘上
  所有人**共用一个桶**，限严了就变成"一个人把一片朋友拖慢"（和当年"一人输错密码锁全站"
  同一类 bug）。实测记录与取值理由都写在配置文件里。

> **这一节的安装要 root**，我这边做不了（sudo 白名单只放了 `systemctl … yanwu`）。
> 命令在 `deploy/DEPLOY.md`：装 → `nginx -t` → 通过了才 `reload`。

## 站点图标（浏览器页签上那方金印）

2026-10-16 加。此前全站**一个图标都没有** —— 页签上是一张白纸，收藏夹里也是。

三份文件，都在 `public/` 下，**都是生成好提交进仓库的**（运行时不生成、没有构建步骤）：

| 文件 | 给谁用 | 形态 |
|---|---|---|
| `public/icon.svg` | 认 SVG 的现代浏览器（Chrome / Firefox / Safari 16.4+） | 矢量，1KB |
| `public/favicon.ico` | 不认 SVG 的（老 Safari、老 IE）、以及**根目录那个裸探测** | 16 / 32 / 48 三档打进一个容器 |
| `public/apple-touch-icon.png` | iOS「加到主屏幕」 | 180×180，**满幅不圆角** |

生成器是 `scripts/make-icon.js`（**一次性工具**，改图标时才跑，不是构建步骤）：

```bash
node scripts/make-icon.js      # 重写 public/ 下那三份，跑完记得提交
```

### 为什么是"金印 + 武"

一方金印：金色渐变做底、墨色的「武」压在正中。渐变那两档直接取色板里的
`--yw-gold-lt → --yw-gold-dk`，和导航栏品牌字前面那根金色短竖（`.topnav .brand::before`）
是同一套颜色 —— 页签上这个方块就是那根短竖的放大版。

**底色选了金而不是墨**（本来更贴"墨金"那套）：页签栏有亮有暗，深墨色的方章在深色页签栏上
整个糊掉，只剩一块看不见的黑。金色两头都压得住，也才认得出是"印"。
字用「武」是因为站名叫演武擂台、榜首那枚章叫演武王，全站其实只讲这一个字。

### 字形是**取轮廓画出来的**，不是 `<text>`

这是这一节里唯一一个"不这么做就会在别人机器上坏掉"的地方：
SVG 里的 `<text>` 要靠**看的人那台机器上装了中文字体**才画得出来，缺字体就是一格豆腐。
而图标恰恰是"必须有"的东西 —— 页签上摆个豆腐块比空白还难看。
所以 `make-icon.js` 自己把 TTF 的 `glyf` 表读出来、把二次贝塞尔转成 `<path>` 写进 SVG：
**出来的 SVG 不依赖任何字体**，谁打开都一样。

几个连带结论：

- 字形来自 **Droid Sans Fallback**（Debian 的 `fonts-droid-fallback`，本机唯一一个带中文的字体），
  **Apache-2.0**，和本仓库同一个许可证，所以抠出来的轮廓可以随仓库公开。
  脚本里的 `ICON_FONT` 可以指到别的字体上（那个字得是**简单轮廓**，复合字形会当场报错，
  不会闷声画错）。
- 假粗：这个字体没有粗体，加粗靠给 `<path>` 描一圈**同色的边**（`BOLD`）。
- 定位按**字形实际外框**算（`FILL` = 占方块边长的比例），不是按字身框 ——
  按字身框算的话「武」会偏上一截，方块下面空一条。
- `test-icon.js` 有一条断言专门盯着"SVG 里不许出现 `<text>`"。

### 引用方式（`views/partials/header.ejs`）

```html
<link rel="icon" href="/public/favicon.ico?v=…" sizes="16x16 32x32 48x48">
<link rel="icon" type="image/svg+xml" href="/public/icon.svg?v=…">
<link rel="apple-touch-icon" href="/public/apple-touch-icon.png?v=…">
```

**ICO 在前、SVG 在后**：认 SVG 的浏览器会挑后面那份矢量图（缩放不糊），
不认的（老 Safari）就用手上那个 ICO —— 两边都照顾到。顺序反了，老浏览器就没得退。
三个 `?v=` 和两个 CSS 一个道理（nginx 给 `/public/` 盖了 `expires 7d`）。

### 根目录那个 `/favicon.ico` 是另一条路

页面上的图标指的是 `/public/favicon.ico`（走 `express.static`）。
另有 `routes/public.js` 里的 `GET /favicon.ico`，服务的是**浏览器对根目录那个固定路径的
裸探测** —— 老 IE、老 Safari 的书签、一部分 RSS 阅读器**不读 `<link>`**，闭着眼睛就来拿它。

★ 这条**必须留在 `routes/public.js`（= `requireLogin` 之前）**：挂到后面，游客拿到的是
登录页的 HTML，浏览器把那张 HTML 当图标存下来就是一张裂图 —— 而且页面看着一切正常。
（和 `robots.txt` 同一个坑，`test-icon.js` 里那条"游客拿图标不会被弹去登录页"钉的就是它。）

它带 `max-age=86400`（一天），比 `/public/` 那 7 天短：这个 URL 挂不上 `?v=`，没法破缓存，
换图标时只能靠短一点的 max-age 少让人等。
（nginx 的 `expires 7d` 只管 `location /public/` 那一段，这条穿过去是 Node 自己发的头。）

### 满幅 vs 圆角：两份故意不一样

页签那份是**圆角方章**（`rx=14`，坐标系 100×100）。iOS 那份**必须满幅、不能留圆角**：
圆角外面是透明的，而 iOS 会用黑色去补圆角外那一圈 —— 于是四角变成四个黑三角。
所以 `apple-touch-icon.png` 是铺满的（圆角由系统自己切）。`test-icon.js` 有一条断言数
"不透明像素是不是满的"，防的就是哪天顺手给它也加上 `rx`。

### 改图标要动哪

| 想改 | 改哪 |
|---|---|
| 换个字 | `scripts/make-icon.js` 的 `CHAR`，重跑 |
| 换配色 | 同上的 `INK` / `GOLD_LT` / `GOLD_DK` |
| 字大一点 / 小一点 | 同上的 `FILL`（默认 0.66）；`RX` 是圆角 |
| 换字体 | `ICON_FONT=/path/to.ttf node scripts/make-icon.js` |

跑完**三份文件都要提交**（它们是产物，但仓库里存的就是产物）。
新库 / 新机器上不需要跑它 —— 只有真想改图标时才需要，而且那时本机得有那么一个 TTF。

> 加了新的 `public/` 文件，记得同步 `.devlocal/test/reset.sh` 里那份**逐个点名**的拷贝清单，
> 否则沙箱里 404、`icon` 那套断言会红得像"代码坏了"。

### 自测

两套，各管一半（`test-icon.js` 51 项 + 浏览器那套 12 项）：

- **`test-icon.js`**（服务端）：三份的字节（ICO 魔数、目录里三张的偏移与 IHDR 尺寸对得上、
  SVG 里不许出现 `<text>`）、两个页面的 `<head>` 引对了没有、游客拿得到、根目录那条裸探测，
  最后**把图解成像素数墨色占比** —— 一头一尾都设卡：全金 = 字没画出来，全墨 = 画糊了。
- **`icon`**（真浏览器，`preview/run-browser.sh icon`）：换 **Gecko 的解码器和画笔**再解一遍。
  服务端那边是 sharp（librsvg）解的，两个渲染器都认才叫"谁打开都一样"；真浏览器还独有两条判据：
  SVG 里那把 `<path>` 画的「武」**真画出来没有**（画到 canvas 上数像素），
  以及 iOS 那份的**四角透不透**（透了就会被系统补成四个黑三角）。
  ⚠️ 这一套的图是**页面里静态写死**的、断言挂在 `load` 上跑的：不能让脚本 `new Image()` 异步等，
  headless Firefox 截完图就退出，异步的 harness 会时红时绿（`_lib.sh` 里记着这个坑）。

## 评论（阵容卡下面的短留言）

2026-10-14 加。每套阵容的卡最下面多一行 `💬 3 条评论`，点开是个原生 `<details>`，
里面是留言列表和一个输入框。**每条最多 20 字。**

| 项 | 结论 |
|---|---|
| 谁能发 | 都行。成员署名自己的昵称（带慧眼圆框、链到个人页），游客一律署名「游客」 |
| 20 字怎么算 | JS 的 `String.length`，和输入框上的 `maxlength="20"` **同一个口径** |
| 放在哪 | 卡内折叠，原生 `<details>`，**默认合着** —— 不点开时整面墙和从前一样整齐 |
| 什么时候能发 | 只要墙上还显示这套阵容就能发，**不跟结算 / 打分封盘一起冻结** |
| 谁能删 | 管理员删任意一条；成员删自己发的；游客发的只有管理员删得掉 |
| 跟谁走 | 跟**阵容卡**（`entry`）走：删赛期连评论一起删；把最后一张阵容图删了、卡从墙上消失，评论也跟着看不见 |

- **为什么不冻结**：打分封盘是因为慧眼等级看那些票，"拖到名次明朗再补票"等于照答案改卷。
  评论不进任何名次、不影响任何计算，没有封盘的道理。
- **为什么统一署名「游客」**：不给填名字的入口，从根上不可能冒充成员。
  代价是同一个人发的几条留言彼此认不出来 —— 这是用户选的取舍。
- **正文一定要走转义输出**（EJS 那个等号写法，不是减号写法）：这是全站唯一一处
  由**没有账号的人**直接写进来的文本，用不转义的那个就是存储型 XSS。
- **20 字按 UTF-16 单元算**：一个汉字 1 个、一个 emoji 2 个。选它是因为它和浏览器的
  `maxlength` 完全一致，不会出现"浏览器让你打字、服务端嫌长"的错位；
  代价是一个 emoji 算两个字（中文够用，不为此引入 `Intl.Segmenter`）。
- **连续空白先折成一个空格再 trim**：只 `trim` 不够 —— 一串全角空格（`　`，`\s` 认它）
  也能凑出一个"看起来是空的 20 字"。
- **留言多了不会把整行卡片顶高**：`.cmt-list` 封了 12rem，超出在卡内滚
  （`overscroll-behavior: contain`，滚到底不带着整页一起滚）。
- **展开一张卡只顶它自己那一列**（2026-10-14 起，`public/wall.js` 把墙拆成了独立竖列）：
  同一排的邻座一个像素都不动，同一列在它下面的整体下移 —— 见「阵容墙的版面」一节。
  没有 JS 时退回从前的样子（grid 行高整排共享，撑开一张整排一起变高）。
- **发完评论是"重定向回那张卡"**（PRG，落回 `#e<id>`）。折叠着的评论区等于"评论发没了"，
  所以 `public/comments.js` 唯一的工作就是：带 `#e<id>` 进来时，把那张卡的 `<details>` 打开。
  没有这个脚本、手点一下 ▸ 照常能用（增强不是依赖，和 `lightbox.js` 同一个约定）。
- **防刷只拦游客**：同一 IP **5 秒 1 条、1 小时 30 条**（`limiter.js` 里和登录失败那套并排，
  共用同一个 sweep）。成员有身份、有人盯着，而且不少成员共用一个出口 IP，按 IP 限他们等于连坐。
  **只在真的写进库之后才算一次** —— 打错字、超长被拒都不吃额度。
- **免登录写接口的 CSRF 面**：评论是全站唯一一个不需要登录就能写的接口，没有 session 可以挂
  token，`sameSite=lax` 也拦不住"游客的第一次提交"（那本来就没有 cookie）。所以多一道 Origin 兜底：
  请求带 `Sec-Fetch-Site: cross-site`，或者 `Origin`/`Referer` 的 hostname 与本站不符 → 403；
  两者都没有（curl、测试脚本）→ 放行。**只比 hostname**：nginx 的 `proxy_set_header Host $host`
  不带端口，按"完全相等"比会把走端口访问的游客全拒掉。
- **不留 IP**：全库到现在没有第二个 IP 字段，不想为留言新引入一份隐私数据。
  副作用是管理员事后查不到"这是谁刷的"，只能删 —— 挡住刷屏的是限流，不是追查。
- **实现**：表在 `schema.sql` 的 `comments`（`user_id` **可空** = 游客，是全库唯一一个可空的
  成员外键）；查询 `db.getWallComments`（一期一次查回来、按 entry_id 归并，照打分的套路）
  挂进 `db.getLineupWall` 的每一行，所以首页的墙和 `/wall` 的墙永远是同一份数据；
  界面在 `views/partials/comments.ejs`；路由在 `routes/public.js`；样式是 `style.css` 的
  `details.cmt` 一节。
- **Pico 的坑（实测）**：`pico.min.css` 里已经有 `details` 和
  `details summary:not([role])` 的规则，特异性比 `.cmt > summary` 高 ——
  选择器**必须写成 `details.cmt > summary`** 才压得住；`details` 和
  `details[open] > summary` 的 `margin-bottom` 都要顶掉（不然每张卡底下白多一截）。
  右侧那个 ▾ 箭头不用自己画，Pico 的 `details summary::after` 已经有了。
- **署名那一行是 `<div>` 不是 `<p>`（实测）**：那一行里装着「删」那个 `<form>`，
  而 HTML 不允许 `<p>` 里放表单 —— 浏览器会自动把 `<p>` 闭合，表单于是被挪到这一行**外面**，
  CSS 里那几条 flex 规则一条都不生效，「删」掉到下一行左对齐。这类错位**不会**被
  "宽度/溢出"那些量法发现（没有任何东西溢出），只能靠一条结构断言盯住
  （浏览器那套里有一条 `closest('.cmt-meta')` 的检查专治这个）。
- **留言的时间当天只写时分**（`14:56`），不是当天才带上月日（`10/13 22:08`）：
  署名 + 时间 + 删按钮要挤在同一行，写全了必折行。见 `app.js` 的 `fmtShort`。

## 结算战报（贴群里那段纯文本）

2026-10-14 加。**每期结算完都要往群里报一次成绩**，从前只能照着页面手打一遍
（或者截图）。现在 `/seasons/:id` 顶上多一个折叠的 **📋 复制战报（贴群里用）**，
点开就是一段排好的纯文本，全选复制就能贴出去：

```
【第32期 · 演武积分赛】21 人参赛 · 8 人交分
👑 王小明  4800 分
👑 张三  4500 分
3. 李四  4300 分
🏆 口碑最好：张三（均分 340 · 5 人打分）
👁 慧眼等级：李四 +5、王五 +2
```

| 项 | 结论 |
|---|---|
| 哪一页 | 赛期详情 `/seasons/:id`，**只有已结算的期才有**。进行中的期这一段整个不渲染 |
| 首行 | **两个数**：`db.countPlayers`（上传了阵容就算参赛）和 `rows.length`（真交了分的）。只报参赛人数的话，下面往往只列得出一小半人，看着像漏了谁 |
| 名次 | 和页面上那张排名卡**同序**（`getFinalRanking`，已结算期的最终名次），**前两名都带 👑**（2026-10-15 起，所以不出现"2."） |
| 口碑最好 | 阵容墙上**互评均分最高**的几位；并列的全列出来，各带各的票数；没人打过票就不出这一行 |
| 慧眼等级 | 本期结算时涨了等级的人（`getEyeAdjustments`）；一个都没有就不出这一行 |
| 默认状态 | 折叠（只占一行）。真要用它的人是刚点完结算、被 302 送到这一页的管理员，一眼就看见 |
| 谁能看 | 任何登录的成员都能看（战报不是管理员的特权），游客进不来（这一页本来就要登录） |

- **⚠️ 「点一下自动复制」在本站是实现不了的，别试着加**：`navigator.clipboard` 要求**安全上下文**，
  而本站只有 HTTP（nginx 只听 80、没有证书、也不打算上）—— Chrome / Firefox 上这个 API
  **干脆就是 `undefined`**。所以 `public/report.js` 只做一件事：把文本框全选上，
  剩下的交给用户（手机上长按选「复制」、桌面上 `Ctrl/Cmd+C`）；顺手试一下
  `document.execCommand('copy')`，成不成都不影响文本框可用。**是增强不是依赖**，
  脚本没加载时手选一样能复制。
- **口碑最好直接读阵容墙排好序的结果**（`getLineupWall`），不另写一条 `GROUP BY`：
  自己算一遍的话口径会跟墙悄悄分家 —— 墙上还包含"传了阵容但没交积分"的人，
  那样就会出现"墙上第一行是甲、战报却写乙"。宁可跟着墙的既有口径走。
- **并列全列**，同 `maxBy` / `minBy` 的处理（只有五档，并列太常见，只挑一个人是误导）。
  均分和人数**逐个人各写一遍**：并列的几条票数往往不一样，共用一个数就成了假话。
- **不列"谁没交积分"**：这是往群里发的**战报**，把缺席名单和冠军排在一起不合适；
  而且已结算的期这么列本来就不准 —— 赛期结束之后才注册的人也会被算成"没交积分"
  （`getNotSubmitted` 是按"启用成员"反推的）。真要看这个，赛期进行中的那一页有。
- **纯文本，不带 Markdown**：QQ / 微信都不渲染，星号井号只会变成噪声。正文里只有两个 emoji。
- **拼在服务端**（`routes/main.js` 的 `buildReport`），不拼在模板里：模板要一格一格输出变量、

## 备份与恢复

```bash
npm run backup          # 保留最近 30 份
KEEP=90 npm run backup  # 保留最近 90 份
```

备份落在 `backup/`，每份两个文件：`app-<时间戳>.db`（`VACUUM INTO` 做的一致性快照，
不用停服务）和 `uploads-<时间戳>.tar.gz`。时间戳是上海时区的 `YYYYMMDD-HHMMSS`。

★ 那个 `uploads-*.tar.gz` **不再是 `tar uploads/`**：图片搬到 R2 之后本地那份压根不更新，
照旧打包等于**图片从此不在任何备份里**（静默的数据丢失，而且不会有人发现，
直到真的需要恢复的那一天）。所以 `scripts/backup.js` 现在的做法是
**先用 `scripts/r2-pull.js` 把对象拉到一个临时目录，再打成 tar.gz，最后删临时目录** ——
和"回滚时把对象拉回 `uploads/`"共用同一份取数逻辑（抄一份到别处迟早会改岔）。

★ 那一步失败**只警告 + 非零退出，绝不抛**，也刻意排在库后面：不能让上面那个库备份白做。

挂到 crontab 每天凌晨 3 点（宿主机时区是 America/New_York，注意换算）：

```cron
0 3 * * * cd /home/raving/work/sanmouyanwu && /usr/bin/npm run backup >> backup/backup.log 2>&1
```

> ⚠️ **其实没装**：2026-10-15 核过一遍，宿主机上并没有这条 crontab，
> 现在是**手动跑** `npm run backup`。`backup.js` 自己补读 `.env`（它的 npm script
> 没有 `--env-file`，而这一步要 R2 凭证；改 `package.json` 加 `--env-file` 会被发布流程拦），
> 所以手动跑不用额外带参数。

**恢复**：停掉服务 → 把 `app-<ts>.db` 覆盖成 `data/app.db`（同时删掉 `data/app.db-wal`、`data/app.db-shm`）
→ `tar xzf uploads-<ts>.tar.gz -C /home/raving/work/sanmouyanwu` → 起服务。

**回滚（退回改造前的代码）要额外一步**：cutover 之后新传的图**只在 R2 上**
（后端不再经手字节，本地 `uploads/` 停在迁移那一刻）。所以先

```bash
node --env-file=.env scripts/r2-pull.js --dest uploads
```

把这些对象拉回 `uploads/`，再回滚代码 —— 否则"回滚回去了，最近的图全没了"。
